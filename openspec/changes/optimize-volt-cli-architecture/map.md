# Structural map — `packages/volt-cli/src`

Phase 1 output of `optimize-volt-cli-architecture`. Written by the main loop from 7 cartographers + 1 seam
analyst; agents never append here. Baseline shape: **118 files / 15,295 LOC / 7 projects** (excl. generated `obj/`).

Two columns carry the weight. **claimed → reached** is where the layering lens starts: every row where they
disagree is a decision made outside the layer that owns it. **hidden edges** is reflection / `dynamic` /
IronPython / COM / string-keyed dispatch — the edges no compiler sees, and the reason an empty `dependents`
means "no STATIC callers", never "dead".

### Seam analyst notes

- THERE ARE NO COMPILE-TIME `up` EDGES. The ProjectReference graph is a clean DAG with a single sink: Volt.Cli.Transport ← Volt.Engine ← {Volt.Cli.Ide.Codesys, Volt.Cli.Ide.Twincat, Volt.Cli}; Volt.Cli.Transport ← Volt.Cli.Connector.Core ← Volt.Cli.Connector. Nothing in a lower project names a type in a higher one. Every reference I found points down or (test-only) sideways.
- The up-ness is in OWNERSHIP, not direction. Volt.Cli.Transport is the sink, so it is where anything two branches must share ends up — which is how `Ops` (the engine's dispatch table), `BridgeErrorCodes` (the engine's domain errors, down to INVALID_ST and DUPLICATE_CHILD), `HealthStatus` (DriverBase's row verdict) and `Vendors` (the drivers' identity) came to live one layer BELOW the only code that decides them. Volt.Cli.Transport is not a transport; it is a transport plus a shared kernel, and the two halves have different reasons to exist.
- The two pipe CLIENTS have opposite DTO policies. Volt.Cli deserializes Volt.Engine's own Wire DTOs directly (BridgeClient.cs:29-56; the class doc calls this out — "no zod schemas, the DTOs ARE the contract"). Volt.Cli.Connector.Core re-declares the health row privately (PerPipeProjectSource.cs:100-102) and is pinned to the real one only by tests in a project that references Volt.Engine for no other reason. Same wire, same process family, two answers to "is the DTO shared or mirrored?".
- The connector's vendor-neutrality claim holds below IProjectSource and breaks above it. PerPipeProjectSource is genuinely vendor-blind (one class, two instances differing by a prefix string). But TwincatSupervisor, TwincatXaeProbe, BridgeSupervisor, WorkerSpec and TrayContext.ReconcileTwincatWorkers exist solely for TwinCAT, and CodesysActivation (a clipboard + message box) is CODESYS's entire counterpart. ARCHITECTURE.md already frames this as the deliberate LIFECYCLE asymmetry — the map point is that the asymmetry sits ABOVE the interface its own doc comment says contains it.
- ItemKind is the single widest shared symbol in the graph and it crosses three project boundaries in three different roles: as the classification target in both vendor gateways (CodesysTypeMap.cs ~35 sites; TcObjectModel.cs + BeckhoffDriver.Tree.cs), as the materialization table inside Volt.Engine, and as the workspace file-extension registry in the CLI (Extensions.cs:21, Scaffold.cs:37). It is also the only reason Volt.Cli references anything in Volt.Engine outside Wire/.
- Volt.Cli.Connector.csproj references Volt.Cli.Transport via `..\..\..\volt-cli\src\Volt.Cli.Transport\Volt.Cli.Transport.csproj` — out of the package and back in. It resolves to the same project every sibling reaches as `..\Volt.Cli.Transport\`, so MSBuild dedupes it; it is a stale path from when the connector lived outside volt-cli, not a second reference.
- `using Volt.Engine;` at src/Volt.Cli/Sync/Commands.cs:2 appears dead: the only public type in that root namespace is `BridgeException`, and Commands.cs never names it (it matches on `PipeCallException.Code` instead — Commands.cs:13-14).
- FakeIde has already been split on the signal the brief flags: FakeIde.cs:104-108 and :225-247 keep `IsConnected` (live) and `BuildHealthResponse()` (cached) as separate sources, with `StaleHealthSnapshot` to model TwinCAT's throttled lag. What remains coupled is that the synthesized rows are still DERIVED from `IsConnected` (`var serving = IsConnected && !StaleHealthSnapshot;`), so the fake can represent the divergence but cannot produce it independently. Reporting only — not proposing a change.
- FakeIde implements IIdeDriver directly and does NOT derive from DriverBase, so nothing in the ~500 unit tests exercises the shared degraded/liveness/single-flight machinery through a driver. `DeriveServedStatus` is tested as a pure static (HonestHealthTests); `SingleFlight`, `RunOnStaThread`'s freshness stamping and `OverlayLiveHealth` are reached only by the live e2e.
- DebugService is confirmed unreachable by construction, not merely by absent static callers: dispatch is an explicit `switch (req.Op)` over `Ops` string constants (BridgePipeHost.cs:55-121) with no `debug` case and no `debug` constant in Ops.cs. Its four supporting members on IIdeSession (`DebugLibrarySignatures`, `DebugItemXml`, `DebugReflect`, plus `IDebugIntrospect`) are therefore dead weight on the vendor seam. Known defect — recorded, stepped around.
- Two loggers write the same format to the same directory: Volt.Engine/Diagnostics/VoltLog.cs (bridges + hosts) and Volt.Cli.Connector.Core/Log.cs (connector + worker stdout re-tagging). Log.cs:6-9 states the reason outright — Core's logger is tied to the bridge's init and the connector may not reference Volt.Engine. Volt.Cli (the CLI) references Volt.Engine and uses neither; it logs nothing.
- Static-search caveats that apply to any deletion decision here: (a) PipeHost.Start/Stop are reached only from IronPython by name; (b) all CODESYS IDE access is reflection/`dynamic` (Ide/Reflection.cs, Ide/CodesysObjectModel.cs) and all TwinCAT IDE access is late-bound COM (Ide/TcPlcOpen.cs:28 invokes ITcPlcIECProject members by IDispatch on a dynamic RCW, and TcPlcOpen.cs:13-20 documents that this is UNVERIFIED against a live IDE); (c) the wire is driven by a string-keyed op table that a TypeScript client re-spells independently (test/e2e/harness.ts) — Ops.cs:8-9 says the two spellings are kept in agreement by hand.
- Two build-time guards act as seams in their own right and constrain any restructure: VendorParityGuardTests scans src/Volt.Engine and fails on a `"twincat"`/`"codesys"`/`"beckhoff"` literal in non-comment code (this is WHY vendor identity had to be placed in Volt.Cli.Transport and why both drivers reach past Volt.Engine to get it); WireVocabularyGuardTests scans all of src for re-spelled vocabulary values with a per-file allowlist that currently names Ops.cs, Program.cs, Git.cs, TcObjectModel.cs, ControlServer.cs, Vendors.cs, HealthStatus.cs, BridgeErrorCodes.cs. Moving a file changes what those guards see.
- test/shared/FakeIde.cs is `<Compile Include>`-linked into three test assemblies rather than being a shared project — so it compiles three times under namespace Volt.Cli.Tests, and Volt.Cli.Connector.Tests pulls it in solely so a live-pipe test can stand up real BridgePipeHosts (its csproj says so). It is the only test double shared across assembly boundaries; FakeProjectSource, FakeBridgeWire and FakeCodeStore are each local to one test file.

**Notes for the diagnosis phase**

- The project is TWO things wearing one name. A wire MECHANISM (PipeServer, PipeClient, PipeDiscovery, PipeMessages — 332 of 432 LOC) and four pure VOCABULARY tables (Ops.cs, Vendors.cs, BridgeErrorCodes.cs, HealthStatus.cs — 73 LOC) that the mechanism almost never reads. Exactly ONE intra-project vocabulary reference exists: PipeServer.cs:90 → BridgeErrorCodes.InternalError. Ops, Vendors and HealthStatus have zero readers inside Volt.Cli.Transport; they live here because it is the lowest project everything else references (Volt.Engine.csproj:23, Volt.Cli.csproj:16, Volt.Cli.Connector.Core.csproj:14, Volt.Cli.Ide.Codesys.csproj:14, Volt.Cli.Ide.Twincat.csproj:15, Volt.Cli.Connector.csproj:20 — all six).
- The op vocabulary and the op TABLE are in different assemblies. Ops.cs:12-19 owns the closed set; Volt.Engine/Wire/BridgePipeHost.cs:55-121 owns the switch and :43 owns the paused-allowlist subset. Nothing in Transport interprets `op` (PipeServer.cs:80 just deserializes it), so the exhaustiveness of the dispatch is checked by no compiler and by no single test — an added const and an added case are independent edits.
- The wire is type-blind in both directions, by construction. PipeFrame.Result/Progress are `object?` (PipeMessages.cs:31-32) serialized by runtime type (PipeServer.cs:116), and PipeClient.Call returns a raw JsonElement (PipeClient.cs:29). So the bytes are decided by Engine DTO attributes + PipeJson.Options, and the parse back is decided independently in Volt.Cli/Sync/BridgeClient.cs:29-56 and Volt.Cli.Connector.Core/WireProjects. No compile-time link ties the frame written to the DTO read.
- Two different JSON policies on one wire. Response frames use PipeJson.Options (camelCase + omit-null, PipeMessages.cs:11-15); request BODIES are re-parsed in Engine with a separate options object, PropertyNameCaseInsensitive (BridgePipeHost.cs:19,156-159). Request and response encodings are therefore not the same decision, despite the PipeJson docstring claiming one encoding for the wire.
- ICodedError is a deliberate inversion running opposite to the layer stack: Transport declares it (PipeMessages.cs:52), Engine implements it (BridgeException.cs:9), PipeServer.cs:90 reads it by runtime type test. Nothing enforces implementation — a non-implementing exception silently becomes INTERNAL_ERROR, which is precisely the mechanism ARCHITECTURE.md:234 relies on drivers not tripping.
- Transport structurally cannot obey Convention 4 ("never swallow a background failure"). It has four bare catch/swallow sites with no log line (PipeServer.cs:62,65,92,94; PipeDiscovery.cs:36), and it cannot reference Volt.Engine.Diagnostics/VoltLog because Engine references Transport, not the reverse (Volt.Engine.csproj:23). An accept-loop bind failure or a partial pipe enumeration is unobservable.
- Two ways to name the same pipe. Per-vendor factories PipeNames.CodesysInstance/TwincatInstance (:20,:22) are used by the HOSTS (Volt.Cli.Ide.Codesys/PipeHost.cs:62, Volt.Cli.Ide.Twincat/Program.cs:43); the generic PrefixForVendor (:26) is used by the CLIENTS (Volt.Cli/Sync/BridgeResolver.cs:29, via ConnectorSetup.cs:25-26 for the connector). Same scheme, two spellings — and the generic one takes a raw lowercased string rather than a Vendors id, so vendor→pipe is unvalidated.
- Dead-ish vocabulary with no static consumers (static search only — see below): PipeNames.Twincat (PipeNames.cs:12) has no reference outside its own file; PipeNames.Codesys (:11) only as the never-observed default at Volt.Cli.Ide.Codesys/PipeHost.cs:23, overwritten at :61-63. PipeClient.MalformedError / NoResult (PipeClient.cs:19-20) have no consumer in src OR test — they exist only so their two throw-sites share a spelling.
- The pipe-NAME scheme is the one wire vocabulary that is NOT guarded. WireVocabularyGuardTests.cs:28-61 covers error codes, ops, vendor ids, health words and item kinds; `volt.bridge.*` is absent, and it is re-spelled as a literal in scripts/codesys-pipe.ps1:11,102, scripts/twincat-instances.ps1:54, scripts/start_volt_codesys.py:7, scripts/build-cli.ps1:4-5, README.md:13, and in C# tests (Volt.Cli.Connector.Tests/ReconcilerTests.cs:25,158; PerPipeProjectSourceTests.cs:46,57,114; WireContractTests.cs:33,55).
- Three independent implementations of one protocol exist. (1) PipeClient (C#). Likewise PipeDiscovery's three kernel32 entry points and the whole JSON serialization path resolve at runtime. Every 'no consumer' claim in these notes means 'no STATIC consumer in packages/volt-cli/src or /test'.

**Notes for the diagnosis phase**

- THE LAYER STACK IS DOCUMENTED TOP-DOWN BUT DEPENDS BOTTOM-UP AT ITS TOP. ARCHITECTURE.md says 'each layer depends only on the ones above it' with Ide/ as the contract at the top. In fact Ide/IIdeSession.cs:3 imports Engine.Wire and returns Wire DTOs (HealthResponse, BridgeDiagnostic) and Library.LibSignature; Ide/DriverBase.cs:5-8 additionally imports Diagnostics and Volt.Cli.Transport. The four other Ide/ files (IProjectTree, ICodeStore, ItemRef, ProjectItem, IDebugIntrospect, PlcOpenTransport) import nothing — so the contract layer is cleanly layered in six files out of eight, and the two that break it are precisely the two that carry health.
- WORKSPACE AND GRAPHICAL ARE MUTUALLY DEPENDENT NAMESPACES. Workspace/Materializer.cs:4 imports Engine.Graphical (GraphicalCode.RenderBody, PlcOpenPouParser); Graphical/PouToXml.cs:5 imports Engine.Workspace (PouData, ItemKind). The cycle is currently harmless only because PouToXml has zero callers — deleting it would break the cycle for free, and adding any second Graphical→Workspace edge would make it real.
- GRAPHICAL DEPENDS ON THE IDE CONTRACT. Graphical/GraphicalCode.cs:3 imports Engine.Ide and takes `ICodeStore`/`ItemRef` as parameters (Read, Write). - THE ITEM 'NAME' IS THE IDENTITY, BUT THREE DIFFERENT NAME FORMS ARE ALL TYPED `string`. **Notes for the diagnosis phase**

- Thread affinity is optional at runtime and nobody notices: CodesysDispatcher.TryCreate() returns null on any reflection miss (Ide/CodesysDispatcher.cs:27-35) and CodesysDriver.MarshalToIdeThread then runs the delegate INLINE on the pipe thread (Driver/CodesysDriver.cs:65). The same null makes IsConnected false (Driver/CodesysDriver.cs:36), so the codebase gives two different meanings to 'no dispatcher' — a hard precondition and a soft fallback — in adjacent lines.
- The wire-visible health shape is composed in the vendor layer. BuildHealthResponse (Driver/CodesysDriver.cs:91-99) does the cache read + TriggerAsyncProbe + OverlayLiveHealth itself, and DriverBase.cs:17-19 already records this as an arch follow-up: 'the wire-visible health shape is composed TWICE (once per vendor) — against parity-critical decisions live in Core, once'. This is a parity-critical decision sitting below the seam by construction, not by accident.
- The gateway reaches two layers up. CodesysObjectModel.ToLibRef calls Volt.Engine.Library.LibraryManifest.Build (Ide/CodesysObjectModel.cs:230) and ExtractLibrarySignatures constructs LibSignature/LibVar/LibMethod directly (Ide/CodesysObjectModel.cs:557-611). - Final workspace TEXT is rendered below the driver seam. Six read-only descriptor renderers live in the gateway (DeviceDescriptor :339, ProjectInfoDescriptor :365, TraceDescriptor :372, TaskDescriptor :382, SymbolConfigDescriptor :432, RecipeDescriptor :438, shared FacetDescriptor :461 — all Ide/CodesysObjectModel.cs), while Core's Workspace/Materializer owns the equivalent for source items. - PLCopen XML is generated in the vendor gateway for interfaces. **Notes for the diagnosis phase**

- TWO OWNERS OF 'previously wanted', and they contradict each other in prose. Reconciler.cs:29-32 states as design: 'Edge-gating also makes a startup grace window unnecessary: after a connector restart previouslyWanted is empty, so there are no leave-edges' — and test/Volt.Cli.Connector.Tests/ReconcilerTests.cs:224 asserts exactly that ('This is what removes the need for a startup grace window'). ConnectionManager.cs:86-91 then does the opposite: it seeds Wanted from wanted.json on disk, which re-creates the leave-edges the Reconciler's contract says cannot exist after a restart, and ConnectionManager.cs:244-255 adds a 20-second GateHold window plus a `_restored` set to compensate. The decision 'does the desired set survive a restart' is made in the outer layer while the inner layer's correctness argument assumes it does not.
- The startup-grace machinery has ZERO test coverage, and it is untestable as written. Grep across test/ for GateHold / grace / _restored returns nothing (only ReconcilerTests.cs:224's comment asserting the opposite premise). ConnectionManager takes an injectable `wantedFile` (ConnectionManager.cs:72,:76) but reads the clock directly (`DateTime.UtcNow + GateHold` at :80, `DateTime.UtcNow < _gateHoldUntil` at :247) — so the one input needed to exercise the window cannot be supplied, even though Reconciler.Plan one layer down does take `nowUtc` as a parameter (Reconciler.cs:44). Time is injectable in the pure layer and hard-wired in the layer that wraps it.
- THE INJECTABLE SEAM EXISTS AND HALF THE TESTS BYPASS IT. ConnectionManager.cs:73-76 documents that `wantedFile` was added because 'two tests failed exactly that way, inheriting a live run's wanted.json'. ConnectionManagerSessionTests uses it everywhere (TempWanted(), :30,43,61,76,94,109,127) — but test/Volt.Cli.Connector.Tests/ConnectionManagerTests.cs:62 is `=> new(sources)` with no wantedFile, so that whole file still reads and WRITES the machine's real %LOCALAPPDATA%\Volt\wanted.json. Same class, two policies.
- 'IS IT SERVING' IS STORED TWICE INSIDE ONE STATE RECORD. State.Serving is a Dictionary<string,bool> (ConnectionManager.cs:38) built by projecting every row's own computed property (`merged.ToDictionary(p => p.Id, p => p.Serving)`, :310) — while DetectedProject.Serving (DetectedProject.cs:34) derives it from Status on demand. Public readers then split: IsServingProject reads the dictionary (:101), Aggregate reads `p.Serving` off Projects (:380). They agree only because both are published in the same `_state` assignment at :311; nothing structurally prevents a future writer from updating one list without the other.
- 'WANTED' IS STORED THREE TIMES: State.Wanted in memory (ConnectionManager.cs:47), wanted.json on disk (:280,:348-356), and `_restored` — a HashSet OUTSIDE the immutable State record (:61), mutated at :136 with no volatile and no interlocked while State itself is carefully published through one volatile field (:63). The class's own concurrency doc (:26-29) says 'everything observable lives in ONE immutable State behind a single volatile field'; `_restored`, `_lastRefreshUtc` (:68) and `_gateHoldUntil` (:60) are three fields that don't.
- THE VENDOR ASYMMETRY IS NOT BEHIND IProjectSource, contrary to both docs. IProjectSource.cs:8-11 calls itself 'the ONLY place a vendor's attach mechanism lives... the boundary the ExternalAttach/InIdeLoad asymmetry is kept behind', and ARCHITECTURE.md:180-182 repeats it. But TwincatSupervisor and TwincatXaeProbe are peers of IProjectSource inside Connector.Core, and their only production driver is the WinForms shell: src/Volt.Cli.Connector/TrayContext.cs:149-160 probes the pids, throttles the tick, spawns and reaps. The TwinCAT-only lifecycle decision is made in the UI layer, above the seam that was built to contain it.
- IProjectSource is a one-implementation abstraction whose reason to exist has been consumed. Since both vendors moved to per-pid pipes, PerPipeProjectSource is 'the ONE IProjectSource for BOTH vendors' (PerPipeProjectSource.cs:11) and ConnectorSetup.Sources() (src/Volt.Cli.Connector/ConnectorSetup.cs:21-26) constructs two instances of the same class differing only in three strings. The single production implementation plus one test fake (test/Volt.Cli.Connector.Tests/ConnectionManagerTests.cs:16) is the whole implementer set.
- THE FAKE-ABLE SEAM THAT LETS A BUG HIDE: PerPipeProjectSource's real constructor takes `Func<IReadOnlyList<string>> livePipes` and `Func<string, IBridgeWire> wireFor` (PerPipeProjectSource.cs:31-38), so every test substitutes both. The consequence is that PipeBridgeWire — where the connect timeout and the Task.Run that makes the whole scan concurrent actually live (IBridgeWire.cs:26,:33) — has no test and no static caller outside the one lambda at PerPipeProjectSource.cs:29. The comment at :42-46 describing the bounded, self-isolating, concurrent fan-out describes behaviour that exists in a different file and is never exercised.
- THE WIRE ROW SHAPE IS DUPLICATED BY HAND ACROSS AN ASSEMBLY BOUNDARY THE BUILD CANNOT SEE. - THE SAME SHAPE IS DUPLICATED A SECOND TIME, IN ANOTHER LANGUAGE. ControlServer.cs:21 (ProjectView) is hand-mirrored at packages/volt-control/src/bridge/connector.ts:24-41, field for field, with the load-bearing projectName-vs-displayName rule stated only in both comment blocks (ControlServer.cs:11-15 and connector.ts:33-36). So one project row is declared three times: Volt.Engine/Wire/ProjectEntry, Connector.Core's private WireProjectRow, and the TS interface — with ProjectView as a fourth re-spelling in between.
- CONTROL-PLANE ROUTES ARE EXEMPT FROM THE VOCABULARY GUARD BY NAME. test/Volt.Engine.Tests/WireVocabularyGuardTests.cs:38-40 lists 'ControlServer.cs' in the exemption set, so 'session'/'sync'/'status'/'workers'/'restart' (ControlServer.cs:136,142,145,165,168) are literals with no central home — unlike the data-plane ops, which come from Transport/Ops. Likewise VendorParityGuardTests.cs:27,:50-57 scopes its vendor-literal scan to src/Volt.Engine only, so Connector.Core is outside both guards.
- CONNECTIONMANAGER DECIDES FIVE DIFFERENT KINDS OF THING IN ONE 387-LINE CLASS: session lifecycle (:116-205), source scanning and merge (:286-313), reconcile application (:236-282), durable desired-set persistence (:333-356), and the tray's colour (Aggregate, :377-385). Aggregate in particular is a presentation decision — it maps model state to a tray icon vocabulary (BridgeStatus) that nothing else in the model uses — sitting in the class that owns the wire scan.
- THE ONE LISTENING SOCKET IN THE TOOLCHAIN LIVES HERE, WITH A HAND-ROLLED ORIGIN CHECK. ControlServer.cs:57,:93 opens HttpListener on 127.0.0.1:8550 and guards it with a string-compare CSRF check at :124-129, while ARCHITECTURE.md:122-123 states the invariant 'the wire is a local named pipe, never a network socket — there is no listening port and no browser-reachable surface, so a web page can't drive push (the HTTP-era cross-origin guard is moot)'. That invariant is scoped to the data plane; the control plane contradicts its literal wording and still carries the HTTP-era guard the doc calls moot. Worth deciding which statement is the intended one.
- REQUEST HANDLING OUTLIVES DISPOSE. ControlServer.OnContext fire-and-forgets `_ = HandleSafeAsync(ctx)` (:111) with no CancellationToken and no in-flight tracking; Dispose (:202-207) flips `_running` and stops the listener but cannot await handlers already inside `_sync` — which is a full ConnectionManager reconcile touching pipes.
- CROSS-THREAD MUTATION WITH NO LOCK, VIA THE CONTROL PLANE.
