Logs & diagnosis

When something goes missing at a customer site — "my POU isn't in the workspace", "a push didn't land" — the durable log is the first place to look. It answers what the bridge did and why it skipped something, after the fact.

Where the logs are

%LOCALAPPDATA%\Volt\logs\

Per-source, daily-rotated files, pruned after 14 days. One location for every component, and it survives a reboot — unlike %TEMP%, which the OS may clear.

filewritten by
codesys-YYYY-MM-DD.logThe in-process CODESYS bridge.
twincat-YYYY-MM-DD.logThe standalone TwinCAT worker.
connector-YYYY-MM-DD.logThe connector / supervisor. A supervised worker's stdout rides in here too, tagged with its own source.

Every line is [timestamp][source][level] message:

[2026-09-23 11:04:18.221][twincat][info] push 3 ops — accepted [created: FooFB.fb] (139 items) (215ms)

To collect a session, zip that folder.

Levels, and what is on by default

levelcarries
errorA failure, with the exception attached.
warnSomething a human should see: an incomplete walk, an item that would not materialize, a folder prune that failed.
infoThe default. The connection and status story, and the push receipt.
debugPer-op mechanics — the fetch/refs tallies and per-item skip names. Off unless you ask.
set VOLT_LOG_DEBUG=1      # then restart the bridge

In-process, VoltLog.Level = VoltLogLevel.Debug does the same. The split is deliberate: Info is what a connection did, Debug is how it did it.

The lines worth knowing

The push receipt — Info

push 3 ops — accepted [created: FooFB.fb; updated: Bar.gvl; deleted: Gone.st] (139 items) (215ms)
push 1 ops — REJECTED (Bar.gvl: item changed since you fetched its version, 0 already applied) (12ms)

An accepted push names exactly what it wrote, grouped by action. A rejected one names the item and the reason, and says how many ops had already been applied — which for a pre-flight refusal is zero, and that is the number to check first when a push half-landed.

The fetch and refs tallies — Debug

fetch init: 138 of 138 project items changed, 0 removed, 412 library signatures (skipped: 2 unmapped-kind, 4 lib-unmatched) (2009ms)
refs: 138 items (140ms)

A clean pull has no (skipped: …) clause. The four drop kinds:

kindmeanswhat to do
unmapped-kindAn IDE item whose kind code is not in the item-kind table.Usually benign — but this is exactly how TwinCAT's DUT subtype codes were silently dropped for months. Debug prints the name and the raw code; check it against the table.
unreadableThe item exists and its body could not be read. The body did not reach the pull.A real error. Logged at Warn with the name and reason, and the names are also on the wire.
lib-render-nullA library sub-signature (a method or property, covered by its parent) or an unknown POU type.Benign — the element rides in its parent.
lib-unmatchedA referenced-library element whose owning library matched no .library reference.It is not dropped — look under Library Manager/(unresolved)/….

The incomplete walk — Warn

fetch: the project walk was INCOMPLETE — 1 folder(s) could not be enumerated (POUs/Machine).
Deletions are suppressed for this fetch: items under those folders were not seen, which is not
the same as gone.

This is the loudest line the sync layer has, and it deserves to be. Deletion is derived from absence, so a folder the driver could not enumerate makes absence meaningless for everything beneath it. The fetch suppresses deletions entirely rather than reporting them, and says so. Before this existed, a single faulting folder deleted the engineer's files for every POU under it.

Diagnosing "my X isn't in the workspace"

  1. Check the wire first. fetch's unreadable list names items the walk found and could not materialize. That is the one failure a client cannot otherwise see — the item still counts toward projectVersion, so it is not reported as deleted, but it has no file. A whole POU once vanished from git silently that way, over a single box whose enable pin read as a boolean.
  2. Search the log for the name — Select-String -Path codesys-*.log -Pattern 'MyPou'.
  3. No hit at Info? Turn on Debug and re-pull. The per-item skip lines name each dropped item and its raw kind code.
  4. Match the kind to the table above. lib-unmatched means it is under (unresolved); unreadable means the Warn line has the reason; an unmapped kind means the kind table has a gap.
"It was excluded from the build in the IDE" is never the explanation. Exclude-from-build is not modelled: an excluded object syncs as an ordinary file like any other, and there is no such drop kind. That explanation was once in this table, with the verdict "expected; confirms the item was excluded, not lost" — a ready-made way to close a genuine missing-item report as normal.

When the bridge itself misbehaves

symptomlook at
Client finds no pipe.Enumerate \\.\pipe\ for the vendor prefix. A pipe named for a dead pid means the bridge outlived its IDE — or, more often, that you are looking at a pid that has since died.
Two workers, one pipe name.Windows will happily split calls between them, and the second serves stale code. Check the worker count is 1 and stop the connector before recording anything.
Everything answers PLC_DISCONNECTED.Either nothing is bound, or a disconnect paused it. Send connect. health still answers while paused — every row reads idle.
An op hangs.A modal dialog in the IDE blocks its automation surface completely. Look at the IDE window.
Calls fail after working.The session is degraded, not dead. The driver's state machine marks it on a dead channel and Recover() re-establishes the binding on the next op. The log says which.
Stale behaviour after a code change.The TwinCAT worker embeds the XAE pid in its pipe name and does not reload on rebuild — rebuild and restart it.

Serving a bridge yourself

One script serves either vendor against a committed fixture project — never the IDE you have open: 

pwsh scripts/ide.ps1 up -Vendor codesys   # or: twincat
pwsh scripts/ide.ps1 pipe                 # print the pipe it is serving
pwsh scripts/ide.ps1 logs
pwsh scripts/ide.ps1 down

The vendors differ in exactly one step and the script owns it: CODESYS loads the bridge in-process, TwinCAT needs a separate VoltBridgeTwincat --xae-pid worker. The IDE stays clickable while a suite drives it, because the IDE's own message loop is what answers the pipe.

Driving one from a test

bun run test:e2e:codesys                  # discovers the live pipe by prefix
bun run test:e2e:twincat

The suites discover the pipe themselves — volt.bridge.<vendor>.<pid>, one per IDE — so there is nothing to hand them. VOLT_PIPE names one directly when you need that.

Never git add -A while an e2e suite is running. A live IDE saves its fixture project to disk as the suite drives it. Stage explicit paths.
