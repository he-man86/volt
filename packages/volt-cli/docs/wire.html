The wire

Eight ops over a Windows named pipe. This is the parity boundary — both vendors answer identically — and it is the thing to build a client against.

Ops:

Transport & framing

One pipe per live IDE: volt.bridge.<vendor>.<pid>, the suffix being the IDE's process id. Clients discover by prefix, because the pid changes on every IDE restart.

The stream is newline-delimited JSON in both directions. A request is one object: 

{ "op": "fetch", "body": { "knownItems": {}, "onlyItems": ["FB_Motor.fb"] } }

A response is a run of frames on the same connection: zero or more progress frames, then exactly one terminal result or error. Each frame carries a single key.

success
{"progress":{"operation":"fetch","done":40,"total":138}}
{"progress":{"operation":"fetch","done":138,"total":138}}
{"result":{"projectVersion":"…","changed":[…],"items":{…}}}
failure
{"error":{"code":"PLC_DISCONNECTED","message":"…"}}

ProgressFrame carries operation, done and an optional total (absent means indeterminate — a build). A multi-phase operation also sets phaseIndex/phaseCount, so a frontend folds the per-phase fraction into one monotonic bar: (phaseIndex + done/total) / phaseCount.

health never blocks. It answers from a cached snapshot and is never marshalled onto the IDE thread, so it is the one op that is safe to poll while a push or a build is running. Everything else takes the IDE.

Identity, versions and the two gates

The item NAME is the identity. refs, fetch's knownItems, every push op and the one-item-per-file layout are all keyed by it. On the wire that name is full — name.kind, e.g. CM_Carrier.fb — because IEC guarantees unique names within a kind, not across them: a control module and the visualization that draws it are legitimately CM_Carrier.fb and CM_Carrier.visualization in the same project. Below the vendor seam the same item is addressed by its bare name, which is the IDE's own lookup key.

versioncoversused by
projectVersionEvery tracked item's content, aggregated.The push lease — expectedProjectVersion.
items[name]One item's content.The per-item optimistic guard — ifVersion.

A push therefore has two independent gates. expectedProjectVersion is the lease over the whole project (what --force-with-lease means); per-item ifVersion is the optimistic check that the item has not moved under you. force drops the per-item checks and keeps the lease. Separately, expectedProjectName/expectedPlatform are an identity check — they refuse with WRONG_PROJECT regardless of force, so a forced push still cannot clobber the wrong IDE.

The push op union

A push carries an ordered list of ops. The wire's op field is the discriminator, and there are two arms — which is fewer than the verbs they cover.

opmeans
set The item named name should end up as toName ?? name, in toFolder ?? (where it is now), with sourceText ?? (what it has now). One op expresses create, update, rename, move and any combination of them, applied atomically.
deleteItemRemove the item.
Absent is not empty, and the difference is load-bearing. toFolder: null means "keep the current folder". toFolder: "" is a destination — the tree root, which on CODESYS is the project's own POU pool. Reading empty as absent once made a drag out of the Application report ACCEPTED, move nothing, and put the file back on the next pull.

Folders are not entities. There is no folder op, because Volt models structure the way git does: a folder is the path an item lives in, created on demand from an item's toFolder, and a push prunes the folders it empties — the way git removes a directory once its last file goes. Only folders that push emptied, recursively up the chain, and never a vendor container.

Error codes

Every failure is a coded error, not a message a client has to pattern-match. The codes are plain strings — nothing in the product branches on them, so a client that wants to react matches the string.

codemeanswhat a client does
PLC_DISCONNECTEDNo project is bound, or the bridge is paused by disconnect.Send connect.
WRONG_PROJECTThe bound project is not the one the request named.Rebind, or refuse — never merge.
BAD_REQUESTA request frame that is not valid JSON, a body that does not deserialize, an unknown op, or a push op the engine cannot route — an empty sourceText, a create with none, an unknown member kind.Fix the caller. The message names the op and the body type.
NOT_FOUNDThe named item does not exist in the project.Re-read refs.
UNSUPPORTEDA shape this vendor cannot write, a member kind with no mapping, or a descriptor field the vendor has no counterpart for. The message says what. Also raised on a READ — a CODESYS member whose type code has no kind.Surface it: a real limit, not a transient. No retry and no edit will change it.
DUPLICATE_CHILDA create collided with something already there.Rename, or update instead of create.
INVALID_CODE_HEADERThe pushed source's header is not one Volt recognises.Fix the file.
INVALID_STThe pushed body failed the ST reader. Raised during a push, so it reaches you on conflicts[].code rather than as an error frame.Fix the body. A network-text refusal also carries a line.
UNREADABLEThe IDE holds the item but its body could not be materialized, so there is no version to compare against. Every refs/fetch names it in unreadable.Fix it in the IDE, or push with force to overwrite it.
NO_SIDECARfetch only: the request carried neither knownItems nor onlyItems, so "everything" and "a client that lost its baseline" are indistinguishable.Send init: true for a first pull, or supply a baseline.
INTERNAL_ERRORAnything thrown that was not an ICodedError. Usually a bug.Collect the log; the message is the exception's own.

Where a code arrives as a conflict, not a frame

Seven of these codes are raised in places whose exceptions the push catches on purpose. They are not lost — they arrive on the conflict — but they never appear as an error frame, which is the single most useful thing to know when a failure does not look like what you expected:

coderaised inreaches you as
UNSUPPORTEDThe push pre-flight, the body-format guard, both drivers.A push rejection — accepted:false, with the code on conflicts[].code.
INVALID_STThe ST reader.Same.
INVALID_CODE_HEADERThe ST header helpers.Same.
NOT_FOUNDThe push, and both drivers.Same, from a push. A driver read during fetch is isolated into unreadable instead.
DUPLICATE_CHILDThe push.Same.
BAD_REQUESTThe push's op routing.Same.
UNREADABLEThe push's create guard.Same.

The optimistic gate's own codes

A rejected push is not an error frame — it is a normal result with accepted:false and a conflicts list, because a version conflict is an expected outcome rather than a failure. Nothing was applied. These five are the gate's own answers, and they are five because the engineer's next step is different for each:

codemeanswhat a client does
STALE_PROJECT_VERSIONThe lease: the project moved between the fetch that produced expectedProjectVersion and this push. Reported on a synthetic row named <project>, which is not an item and cannot collide with one.Pull, then push again.
STALE_ITEM_VERSIONThat item moved since you read its version — the ordinary edit collision. yourVersion and currentVersion are both set.Pull that item, merge, push again.
ITEM_EXISTSA create (ifVersion: null) landed on a name the IDE already holds.Fetch its version and push an update, or pick another name. Not pull-and-retry.
ITEM_MISSINGYou quoted a version for an item that is gone. currentVersion is null. Only ever answered from a complete walk.Nothing to merge with — create it, or drop the op.
ITEM_UNVERIFIEDThe push could not READ the item — the pre-apply walk skipped the folder it lives in, so absence proves nothing. The opposite news to ITEM_MISSING: the item is almost certainly still there and the bridge is what is impaired.Fix what stops the IDE enumerating that folder (see unwalkedFolders). Do not recreate the item.
Match conflicts[].code, never the message. Three vocabularies share that field and they cannot collide: the four gate codes above, a NETWORK_* diagnostic with a line for a graphical body the format refuses, and the seven bridge codes in the table before it. Every conflict carries one.

Until 2026-09 this field held the network-text code and nothing else, so the bridge codes arrived as prose; the gate's four kept arriving as prose after that, all four as code: null, told apart only by which version field happened to be null. The callers did what callers do — the e2e suite asserted on exact English sentences and the CLI printed the message with no branch. If you are reading an older client, that is what you are looking at.

The other closed vocabularies

Three more sets of strings travel on this wire. Like the error codes they are plain strings, defined once, and a client matches them rather than branching on a type.

fieldvaluesmeaning
ProjectEntry.status The ROW's full connection state, and the one self-describing field — "is it serving" derives from it (status != idle), so there is no separate flag. idle = detected but not the served one; healthy/degraded = served, channel fine / had recent errors.
HealthResponse.statusunavailable + the above The BRIDGE-level aggregate. unavailable is a bridge word, never a row value.
BridgeDiagnostic.severity Mapped from the vendor's own severity word by substring, case-insensitively — the inputs are not a closed set. Anything unrecognised becomes info, which is the safe direction: inventing an error would fail a build that passed.
vendor / expectedPlatform The only vendor fact above the seam.

Building a client

volt-bridge.openrpc.json describes everything on this page in machine-readable form, so a typed client is one command: 

npx @open-rpc/generator                      # a typed client
https://inspector.open-rpc.org               # browse it interactively

What the document does not carry is the framing — newline-delimited {op, body} with a leading progress stream — and the per-op error sets above, which ride as x-errorCodes. Generated clients hand you the method signatures; the transport and the failure handling are yours.
