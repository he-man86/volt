The wire

The ops a Volt bridge serves over a Windows named pipe. This is the parity boundary — the same object answers with the same text on both vendors, and what one vendor cannot hold it refuses by name (items) — and it is the thing to build a client against.

Ops:

Transport & framing

One pipe per live IDE: volt.bridge.<vendor>.<pid>, the suffix being the IDE's process id. Clients discover by prefix, because the pid changes on every IDE restart.

rulethe wire
connectionOne request per connection. The client writes one request; the bridge answers and closes the connection after the terminal frame, whatever it is. Concurrent requests use separate connections.
encodingUTF-8 without a BOM. Every frame is one JSON object on one line ending in \n. A request may end in \r\n. A request that starts with a BOM is BAD_REQUEST; a request with no \n is answered once the client closes its side.
sizeA request is at most 64 MiB (67108864 bytes), the newline excluded. A longer one is answered BAD_REQUEST without being parsed.

A refs that arrives while one with the same body runs joins it: it receives the running one's frames from then on and the same terminal frame. Nothing is kept once it answers; the next refs walks again.

health never blocks. It answers from a cached snapshot and never takes the IDE thread, so it is the one op that is safe to poll while a push or a build is running. Everything else takes the IDE.

What a bridge states about itself

health carries the bridge's catalog, from its host's own declarations. A value the bridge does not list there is one it never sends, so a client reads them instead of hard-coding them.

A client reads health before any other op and refuses a bridge whose answer has no languages or no kinds: that bridge is of an older wire, and nothing is sent to it. An empty list is a fact and passes. The CLI refuses it BRIDGE_PREDATES_WIRE (a CLI code, never on the wire); the connector lists it under refused with that code and gives it no project row.

Identity, versions and the two gates

The item's PATH is its identity: its folder in the IDE's own tree and its file name with the kind, <folder>/<name>.<kind>. refs, fetch's knownItems and onlyItems, every push op and its conflicts, a build diagnostic, a grep match and the workspace layout are all keyed by it and all call it name, so two PLC_PRG.pou in two applications are two items, and so are CM_Carrier.pou and CM_Carrier.visualization in one folder.

A path you address (onlyItems, a push op's name and to) finds the IDE item ignoring case, and every answer spells it as the IDE does. A key you hold (knownItems) is exact: a case-only rename in the IDE is the old key in removed and the new one in items. A project name (connect.project, expectedProjectName) is compared like a path, ignoring case; expectedPlatform takes a row's vendor.

A path a push names is one refs could publish: its extension names a kind and a name comes before it, and each folder is spelled as refs spells it — no empty segment, and %XX for a character a path cannot hold or a space or dot at either end of a name (A%2FB, %2EHidden). A set's to names the kind its name does: a re-type is a deleteItem and a create. Anything else (a//b/X.pou, ../X.pou, X.pou → X.gvl) is refused BAD_REQUEST before anything is read or written, forced or not.

Every item path on the wire has this form, readable or not. unreadable lists the items the walk found and did not read, each { name, code, reason } with name the path the item has in items while it reads — the name a forced deleteItem addresses it by. unreadableNodes lists the tree nodes with no file the walk did not read, each { name, code, reason } with name the node path <folder>/<name>: a container holding a setting no text spells, or an object whose kind the IDE could not state (its folder and subtree are then in unwalkedFolders). code is UNREADABLE (the IDE did not give what Volt asked of the object), UNSUPPORTED (the object holds what Volt's text has no spelling for, or sits in a folder excluded from the build), or the code of the read that failed. An object whose name the IDE does not answer is in neither list: it has no path, and its folder is in unwalkedFolders.

refs and fetch state the root path of every application in applications. An item belongs to the application whose root is the longest prefix of its path, matched by whole segments (A/App holds A/App/X.pou, not A/App2/X.pou); an item under none belongs to the pool. A client never parses a vendor segment. A client that sends knownItems also sends the applications its baseline was read with, as knownApplications: a known path under a folder the walk could not read is then judged by the application it was in. A client that does not know them sends none, and such a path outside every application the walk states is then never judged removed. build takes the same roots as applications to compile those alone; without it every application is built.

The two gates

versioncoversused by
projectVersionEvery tracked item's content, aggregated.The push lease — expectedProjectVersion.
items[path]One item's content.The per-item optimistic guard — ifVersion.

A push therefore has two independent gates. expectedProjectVersion is the lease over the whole project: when it is not the project's version the push is refused STALE_PROJECT_VERSION and nothing is applied. Per-item ifVersion is the check that the item has not moved under you; force skips every per-item check and keeps the lease. expectedProjectName/expectedPlatform are an identity check — they refuse with WRONG_PROJECT regardless of force. A write — push and build — must send both: one absent or empty is BAD_REQUEST naming it. On refs, fetch and grep they are optional, and a read answers the platform/projectName it walked.

A quoted version must hold; without one, a set creates and a deleteItem asks only for the goal:

With force, no row's conflict is answered: each op is applied to what the IDE holds. The gate runs over the batch in order, so an op sees what the ops before it did (a create makes the path exist for a later op). A set whose to lands on a path the IDE holds is ITEM_EXISTS from the pre-flight, forced or not, and so is a create or a rename onto a name a POU, DUT or GVL of the same application holds in another folder or kind (the IDE holds one object of a name per application): name is the op's, existing the path of the item there when it is another one, and currentVersion that item's version.

The push op union

A push carries an ordered list of ops. The wire's op field is the discriminator, and there are two arms — which is fewer than the verbs they cover.

opmeans
set The item at path name should end up at to ?? name, with sourceText ?? (what it has now). A path that names no item is a create there. One op expresses create, update, rename, move and any combination of them, and it is one op: it answers one conflict or none. A move stays inside one application; a to in another application is refused BAD_REQUEST naming both (moving there is a delete and a create).
deleteItemRemove the item, guarded by its ifVersion as the table above says.
One op per item. A push names each item in at most ONE op — by its name or a set's to, an addressed path (identity). A second op on the same path (deleteItem X.gvl beside set X.gvl, in either order, or a rename onto a path another op sets) is refused BAD_REQUEST before anything is applied: an update, a rename and a move are one set; a delete and a create of the same path are two pushes, and so is freeing a path and moving onto it. X.pou and X.dut are two items, but ONE IDE object name (the IDE names an object without its kind): a deleteItem of one beside a set of the other is a re-type in one push, and is refused the same way.
The text carries the object's properties. A sourceText spells, besides its declaration and body, every object property the vendor holds as %-lines (%CLASS, %EXCLUDE_FROM_BUILD, …) — so a set whose lines differ from the IDE's is a change even when its code is not. A create makes the class its %CLASS line names, or is refused UNSUPPORTED by name; an update whose %CLASS differs from the IDE's is refused the same way (a class never changes in place — delete and create it, two pushes). Inside a POU, a member renamed in one push keeps its IDE object when exactly one member of its kind was dropped and one added; a member whose kind changes under the same name is refused.

Folders are not entities. There is no folder op: a folder is the path an item lives in, created on demand from an item's path, and a push prunes the folders it empties, recursively up the chain — only folders that push emptied, and never a vendor container.

A POU is X.pou

Every PROGRAM, FUNCTION_BLOCK and FUNCTION travels as X.pou (items), so a push that changes what a POU's text declares — a PROGRAM rewritten as a FUNCTION_BLOCK — is an ordinary content update of X.pou, gated by its ifVersion like any update. The text is written as sent and never read for a kind. A create seeds a function block and writes the declaration before it creates the members, so a member the IDE will not take under that text (a METHOD under FUNCTION text) is refused UNSUPPORTED with the IDE's own message. X.prg, X.fb and X.fun name no kind and are refused BAD_REQUEST.

A DUT is X.dut

Every DUT travels as X.dut, whatever its shape (items), so a push that changes a DUT's subtype — a struct rewritten as an enum — is an ordinary content update of X.dut, gated by its ifVersion like any update. The text is written as sent and the IDE's build reports what is wrong with it. A delete names one item by its kind: deleteItem X.dut never deletes an X that is a POU, forced or not. A name with no kind extension is refused BAD_REQUEST before anything is read: X, X.foo, X.struct, X.enum, X.union, X.alias.

What of the refused op the IDE kept is stated on its conflict: partiallyApplied: true when any of it stays (re-read the item before retrying it), renamedTo with the item's current path after a rename that ran before the refusal, remains: true for a create whose rollback failed — each absent when it does not apply. A reason describes the refusal and carries no client instruction.

The canonical layout

A fetch returns an item's text in one layout. Each rule states what a push of a text that breaks it does: accepted and fetched in this layout; accepted and fetched as pushed, because what breaks the rule is the item's own text; or refused INVALID_ST. Compare a pushed text against the fetched one, or against these rules, never byte for byte against what was sent. A sourceText that starts with U+FEFF is refused BAD_REQUEST. The examples are the writer's own output; in them · is a trailing space and ⏎ the LF that ends a line.

Building

  "diagnostics": [ { "name": "Device/Plc Logic/Application/FB_Motor.pou", "member": "Execute", "code": "C0046",
                     "severity": "error", "message": "Identifier 'x' not defined" } ] }

success is each vendor's own signal: CODESYS has it from its diagnostics, TwinCAT from the IDE's count of failed projects. A failed build always carries at least one error diagnostic: when the IDE wrote none Volt could read, one diagnostic says so, with no item and no position. Never derive success from the diagnostics.

membermeans
nameThe item's path, absent when the vendor named none or one Volt could not resolve to exactly one item.
memberThe method, property or action of name the diagnostic is inside; never without name.

severity, from the host's declared table of the vendor's values; absent when the vendor's value is not in it — not classified.
line, column1-based, a line of the item's fetched sourceText (the coordinates of grep), never the vendor's own count; absent when the vendor stated none or the bridge cannot place it in that text with certainty (a property accessor's line, a network or hidden body). CODESYS states no position; TwinCAT states a line and no column.
durationMsHow long the build took, in milliseconds.

Searching: grep

grep searches the text fetch ships, line by line, and answers lines — never sources: 

{ "op": "grep", "protocol": 1, "body": { "pattern": "lamp", "paths": ["**/*.pou"] } }

{ "matches": [ { "name": "POUs/PRG_A.pou", "line": 7, "text": "\tlamp := start AND NOT stop;" } ],
  "items": { "POUs/PRG_A.pou": "3f2a9c01d4e5b6a7" },
  "searched": 12, "totalMatches": 1, "truncated": false,
  "notSearched": [ { "name": "POUs/PRG_B.pou", "code": "UNSUPPORTED", "reason": "its body reads IMPLEMENTATION CFC UNSUPPORTED" } ],
  "unwalkedFolders": [] }

Line 7 is line 7 of that item's fetched sourceText, and text is that line byte for byte, so it can be quoted back in a push. A line longer than 500 UTF-16 code units is cut to its first 500 (499 when the 500th would split a surrogate pair), followed by …, and the match carries cut: true; a whole line has no cut. items holds each matched item's refs version. pattern is a .NET regular expression, or plain text with literal: true; case is ignored unless caseSensitive: true. In paths, * stays within a segment, ** crosses segments and ? is one character. At most limit matches (default 200, 1–1000) are answered; totalMatches counts to 10000. .library items and library signatures are not searched.

Codes

Every failure is a coded error, not a message a client has to pattern-match. A code arrives on one or more channels: an error frame (the op answers nothing else), a push conflict (on conflicts[].code, beside the ops that landed), or an unreadable entry. Every op may answer as a frame (health never IDE_UNSUPPORTED); each op's own frames are on its card below.

codemeanswhat a client does
PROTOCOL_MISMATCHThe request states no protocol, or one this bridge does not speak. Refused before the body is read; nothing ran. error.data.bridgeProtocol is the number the bridge speaks.The client and the bridge are of two releases: update the older one (an IDE that loaded the previous bridge is restarted).
STALE_PROJECT_VERSIONA push’s expectedProjectVersion is not the project’s version: the project moved since the read that produced it. Nothing was applied. error.data.currentProjectVersion is the version the IDE holds.Pull, then push again.
PLC_DISCONNECTEDNo project is bound, or the bridge is paused by disconnect. When a project is open and cannot be served (a TwinCAT window whose solution has no file), the message says why.Send connect, or do what the message says.
IDE_UNSUPPORTEDThe IDE the bridge runs in lacks something the bridge needs. When the bridge needs it for everything, it serves nothing: every op but health answers with it. The message is fixed English naming the platform version and what is missing — CODESYS 3.5.17.0 is not supported: it lacks … — and health carries the same sentence as unsupported, beside ideVersion. Refused by capability, never by version number. When one call needs it — a type, member or overload of the IDE’s object model this version does not have — that call answers it: as a frame, a push conflict, or the code of an unreadable entry, the message naming what is missing.Show the message; do not retry. The IDE has to change, not the call.
IDE_BUSYA push or build arrived while another push or build held the IDE. Refused at once, before the IDE is touched: nothing was applied and nothing compiled. Reads and health are never refused with it; they wait for the IDE.Wait for the running build or push to answer, then try once. Never retry in a loop.
WRONG_PROJECTThe bound project is not the one the request named. The message names what the request stated and what the bridge serves.Rebind, or refuse — never merge.
BAD_REQUESTThe request breaks the wire’s own rules, whichever phase meets it: a request that is not valid JSON, is over the size limit or starts with a BOM; an unknown envelope member or op; a body that does not deserialize, a body member the op does not have (member names match exactly), a null for a member the schema types as a value or as a list or map entry (null is “absent” only for an optional member); a fetch with neither knownItems nor onlyItems nor init: true; a malformed .task descriptor, a sourceText that starts with U+FEFF (a byte-order mark: the text is UTF-8 text), a push of a kind that is not writable, a move of an item that is no source item, or a push op the engine cannot route — a create with no sourceText, an unknown member kind, a name with no kind extension, a path refs could not publish or a to of another kind (identity, a POU is X.pou, a DUT X.dut).Fix the caller. The message names the op and the member.
IDE_LOST_ITEMA post-condition of a push: the IDE no longer holds what Volt just wrote or read during the apply — a member it created and cannot find again, a node not where the move put it, a task it acknowledged and does not list. Never “the request names nothing” — that is the gate’s ITEM_MISSING, answered before anything is written.Pull to see what landed, then push again; if it repeats, collect the log.
UNSUPPORTEDThe IDE, or a documented Volt limit on a vendor shape, will not take what was sent — never Volt’s own rule about a request (BAD_REQUEST) and never a Volt bug (INTERNAL_ERROR). A shape this vendor cannot write, a create, import or task call-list rebuild the IDE refused, a value the IDE refused, a build of a project with no application, a member kind with no mapping, a descriptor field the vendor has no counterpart for, a %-line this vendor has no measured member for, a class it cannot create, or a member re-typed under the same name. The message says what. On a read: an object holding what no text spells, or an item in a folder excluded from the build (listed unreadable, never pulled without it), and a body that reads IMPLEMENTATION <LANG> UNSUPPORTED in grep's notSearched.Surface it: a real limit, not a transient. No retry and no edit will change it.
DUPLICATE_CHILDA collision below the item: a member the push creates where the IDE already holds one of that name.Rename the member, or update instead of create.
INVALID_STA POU's or an interface's text could not be split into what the push writes: no IMPLEMENTATION line or END line, a body that contradicts the language its line states, a CHILD (METHOD, ACTION, PROPERTY and its GET/SET) whose header cannot be read, or a %-line out of place, out of order, repeated, or with a value it does not take — named with the item and the line. A top-level item's header is never read, and a DUT or a GVL is never refused by it: those are written as sent, and the IDE's build reports what is wrong with them.Fix the body.
UNREADABLEThe IDE holds the object but did not give what Volt asked of it (its body, its kind, its properties), so there is no version to compare against. Every refs/fetch names it in unreadable or unreadableNodes; a push op that would land on it is refused with it.Fix it in the IDE, or push with force to overwrite it. An item the IDE does not return at all (a member it holds no declaration for) cannot be updated in place, forced or not — the refusal says so: push its deleteItem, then push it again as a create.
INTERNAL_ERRORA Volt bug: Volt’s own broken invariant (a state Volt’s code guarantees cannot happen, which the message names), or an exception of the IDE’s own API that Volt did not classify. A request, an IDE state or a vendor limit is never this — each carries its own code: an unreadable folder is ITEM_UNVERIFIED, an IDE refusal UNSUPPORTED, an API this IDE lacks IDE_UNSUPPORTED, a broken post-condition IDE_LOST_ITEM, a member the IDE holds no declaration for UNREADABLE.Report it with the log, which holds the whole exception.

The gate's codes

The per-item gate answers on the conflict, and its codes differ because the engineer's next step does (the gate table):

Building a client

volt-bridge.openrpc.json describes everything on this page in machine-readable form, so a typed client is one command: 

npx @open-rpc/generator                      # a typed client
https://inspector.open-rpc.org               # browse it interactively

The framing is in the document's info.description and its Request, ProgressFrame and ErrorFrame schemas; each op's error frames ride as x-errorCodes. Generated clients hand you the method signatures; the transport is yours.
