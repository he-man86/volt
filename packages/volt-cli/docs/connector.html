The connector

The tray supervisor that decides which bridges run. Its control plane is a small HTTP API on localhost:8550 — orchestration only; PLC code never travels here, that is the wire.

Sessions, not commands

A client does not tell the connector to start or stop a bridge. It declares which projects it is using, and the connector reconciles the running bridges to the union of every live session's interests. A client that goes away stops renewing, its interests leave the union, and a bridge nothing else wants stops on its own.

sequenceDiagram participant C as client (VS Code / desktop) participant K as connector :8550 participant B as bridges C->>K: POST /session K-->>C: { sessionId, leaseSeconds } loop while the client is alive C->>K: POST /session/{id}/sync { interests } K->>B: reconcile to the union of all sessions K-->>C: ConnectorView end C->>K: DELETE /session/{id} K->>B: stop what nothing wants
status is the ground truth, not the list. A disconnected bridge stays listed — that is how you reconnect to it. Serving is status != "idle". Reading "it appears in the list" as "it is connected" is what once let a UI claim a connection against a gated bridge.

Reaching it

Fixed port 8550, overridable with VOLT_CONTROL_PORT — which exists for the live-test tier, so an unattended run can stand a second connector beside the engineer's without fighting it. Localhost only, and a request carrying an Origin header is refused 403: this is not a public API, and a page in a browser is not a first-party client.

That refusal is why the console below proxies through the volt process instead of calling :8550 from this page. The 403 is the control plane behaving correctly.
