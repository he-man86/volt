Network text

Volt's own textual language for FBD and LD graphical bodies — a network of boxes and wires rendered as readable, ST-flavoured text. It exists so an agent or a language server can work over a graphical body as text, even though it was drawn in the vendor's editor.

CFC, SFC and IL are not network text and are not bodies in this sense: they materialize as a marker and are refused on push, never flattened to ST. Both vendors produce identical network text for the same logic — the form has no vendor-specific syntax.

Type checking, undeclared variables, unknown pins, dead labels, hover, completion, navigation. This page is written so that job can be implemented.

Both halves are the same model and the same two converters on both vendors. The round trip is exact: the reader is the writer's inverse, and a body that does not re-emit identically is refused rather than quietly rewritten.

The declaration/body split

A materialized graphical POU is an ordinary ST document. The declaration is normal ST and belongs to the POU; the body is everything from the first NETWORK marker onward, and the reader is handed only that. A graphical POU's declaration is edited in the IDE; a push writes the body. 

PROGRAM Foo
VAR
    a : BOOL;
    out : BOOL;
END_VAR

NETWORK 0 FBD
  out := (a AND a);
END_NETWORK
END_PROGRAM

This matters for type inference: a wire carries no written type, so the LSP infers it from the defining expression and from the declaration it can see — the reader never needs to.

Five design rules

  1. It reads like real ST. A producer wired to exactly one consumer is inlined into that consumer's expression. Only a producer that fans out gets a name. out := ((a AND b) OR c), not a four-line node-per-wire transcript.
  2. Round-trip-exact. write(read(x)) == x is enforced, so there is exactly one canonical text for any body and it never silently reformats or drifts on the next pull.
  3. Topology-exact, no precedence. Every operator group is fully parenthesised. The parentheses are the wiring, so a parser needs no precedence table.
  4. The body parses without the declaration. A wire's nature is marked at its definition, with LET. A bare assignment is a sink.
  5. Wire types are never written. The old form wrote a synthesised type and got it wrong; this one cannot, because there is nothing to get wrong.

Lexical structure

Line-oriented: one statement per line, terminated by an optional ;. Leading and trailing whitespace is insignificant, blank lines are ignored. Keywords, operators and modifier words are case-insensitive; identifiers are matched ordinal, because they are real PLC names and must round-trip verbatim. Keywords are recognised on a word boundary, so LETTER and RETURNED are ordinary names.

The empty slot — a pin connected to nothing

An unconnected input is written as nothing at all, in whichever operand position it occupies:

( * iRPM * 6)                       // a 3-input MUL box whose first pin is unwired
ctu(CU := a, RESET := , PV := )     // named pins with nothing on them
f(, a);   f(a, )                    // positional slots, leading and trailing
coil := ;                           // a rung nothing drives
;                                   // an item wired to nothing at all

It is a position, not a token, and that is deliberate. A sigil was tried first (?) and withdrawn: CODESYS writes ??? into a box whose instance is unresolved — a real compile error the engineer needs to see — so ? was already content. Volt carries ??? through verbatim rather than claiming a spelling of its own. Because the grammar is fully parenthesised with no precedence, every operand sits between two structural marks, so hitting the next mark where an operand should have started (end of input, ), ,, or an operator) says unambiguously that the pin is wired to nothing.

An operator still needs a right-hand operand: (a AND ) is refused. The asymmetry with ( * iRPM * 6) is honest rather than tidy — the empty first pin is measured in a real project, the empty right-hand one is not, and Volt refuses shapes it has not seen rather than inferring them.

DISABLED is a header keyword and is recognised only after the title, never inside it — a network titled TITLE: "DISABLED during commissioning" stays enabled. The optional header fields are named and order-independent, because LABEL and TITLE are two different things and both vendors carry both. The label was a myLabel: line in the body until it was moved: that modelled a property of the network as a statement, and it is now refused with a message naming the header field.

Grammar

program        = declaration , body ;
declaration    = (* ordinary ST — NOT parsed by NetworkTextReader *) ;
body           = { network } ;

network        = network-header , { statement } , "END_NETWORK" ;
network-header = "NETWORK" , integer , language , { header-field } , [ "DISABLED" ] ;
header-field   = ( "LABEL:" , identifier ) | ( "TITLE:" , title ) ;   (* named; order-independent *)
title          = '"' , { char - '"' | '""' } , '"' ;          (* a literal quote is DOUBLED *)
language       = "FBD" | "LD" ;

statement      = wire-def | sink | call-stmt | en-eno-if | execute-box
               | control-flow | comment | empty-stmt ;

wire-def       = "LET" , name , ":=" , producer , [ ";" ] ;   (* an internal wire *)
sink           = lvalue , assign-op , operand , [ ";" ] ;     (* an outVariable / coil *)
assign-op      = ":=" | "S=" | "R=" ;                         (* the coil KIND lives here *)
call-stmt      = call , [ ";" ] ;                             (* an FB instance, OR a box whose *)
                                                              (* output goes nowhere: MOVE(g0, iDec); *)
empty-stmt     = ";" ;                                        (* an item wired to nothing at all *)
en-eno-if      = "IF" , name , "THEN" , ( wire-def | sink | fb-call ) , [ ";" ] , "END_IF" ;
execute-box    = [ "IF" , name , "THEN" ] ,
                 "EXECUTE" , st-text , "END_EXECUTE" ,        (* st-text kept byte-for-byte *)
                 [ "END_IF" ] ;                               (* present iff the box has a wired EN *)
control-flow   = jump | return ;                              (* a LABEL is a header field *)
jump           = "JMP" , name , [ ";" ]
               | "IF" , operand , "THEN" , "JMP" , name , [ ";" ] , "END_IF" ;
return         = "RETURN" , [ ";" ]
               | "IF" , operand , "THEN" , "RETURN" , [ ";" ] , "END_IF" ;
comment        = "//" , text ;

producer       = group | call ;
operand        = empty
               | [ "NOT" ] , core , [ "RISING" | "FALLING" ] ;
empty          = (* nothing — a pin connected to nothing *) ;
core           = group | call | member | name | literal ;
group          = "(" , operand , operator , operand , { operator , operand } , ")" ;
                 (* exactly ONE operator kind per group; fully parenthesised; no precedence *)
call           = [ name , ":" ] , name , "(" , [ args ] , ")" ;
                 (* the leading `name :` is the INSTANCE, written only when it is ??? *)
member         = name , [ ws ] , "." , [ ws ] , name ;

fb-arg         = name , ":=" , operand ;
out-arg        = name , "=>" , lvalue ;
args           = ( operand | out-arg ) , { "," , ( operand | out-arg ) }
               | ( fb-arg  | out-arg ) , { "," , ( fb-arg  | out-arg ) } ;
operator       = "AND" | "OR" | "XOR" | "+" | "-" | "*" | "/" | "MOD"
               | ">" | "<" | ">=" | "<=" | "=" | "<>" ;

lvalue is any ST l-value the IDE accepts (a variable, struct.field, array[i]); the bridge treats it as opaque text.

The model it projects

Network text is a 1:1 textual projection of Format/Network/NetworkModel.cs — a body is a list of networks, each holding statement trees. Every record there carries the vendor measurement that shaped it, and it is kept current because the readers and writers compile against it.

nodeis
LeafA bare operand in tree position — the vendor's BoxTreeOperand.
AssignA coil or outVariable. Via its flags it is also JMP and RETURN. It has a list of targets, not one.
BoxA call or operator — BoxTreeBox. Carries its inputs, its output pins, an optional wired Enable, and an optional StCode for an Execute box.
DemuxFan-out — one wire feeding several consumers, keyed by VarId. This is the vendor's own item, not a Volt construct.
ParallelAn LD parallel branch.
TerminatorThe end of an LD rung.

A Network also carries Title, Label, Comment and Disabled, all four of which both vendors hold on their own INetwork. They were absent from an earlier model because PLCopen carries none of them — and worse, its export omitted a disabled network entirely, which is how a disabled network could be dropped out of a running program.

Flags ride on the operand, not only on the node. A real assignment target came back as Flags=Negation,Set — a negated set coil, with the modifiers on the target. And those two bits are one enum with four values, not two independent modifiers: Negation+Set is reset. Reading them independently made every reset coil in a project materialize as a plain SET — 128 of them in one project, each one inverted, and nothing in git showed it because the text Volt wrote was self-consistent.

Wire vs sink — the central distinction

writtenis
sinkout := <expr> A value CONSUMER — an outVariable or coil. out is a real l-value declared in the POU's VAR section.
wireLET g1 := <expr> A LABEL for a producer, so two or more consumers can reference the same box. The name is not a node of its own.

Inlining is what makes the text readable. A producer wired to exactly one consumer emits no statement of its own — it is inlined into that consumer's expression. A producer that fans out must be named, because inlining it would duplicate its box.

flowchart TD P["a producer
(a box, or an opaque leaf)"] --> Q{"how many
consumers?"} Q -->|one| I["inlined into the consumer
out := ((a AND b) OR c)"] Q -->|"two or more"| N["named — it reaches the IDE

A LET name used ONCE is a textual convenience and is substituted back into its consumer on read. A name used TWICE OR MORE is a structure, and it does reach the IDE: it becomes the vendor's own fan-out item. (This inverts what the spec said for a while — that LET names never reach the IDE and are stripped on push. That was true of the PLCopen transport, where wiring travelled as numeric ids and a name had nowhere to go.)

Pins

A box input is Input(Formal, Value, Flags). Operator and function pins are positional; FB instance pins carry the real parameter names (IN, PT, …). Flags on a pin is how a per-pin negation or edge is carried — the vendor keeps these in its own per-pin field, so a modifier on one input of a three-input box survives.

The four LET families

A LET name's prefix carries its meaning. These are the names the writer mints for exactly these four things, and a reader honours the prefix rather than guessing from how often the name is used. A name the writer did not mint is hand-authored, and there use count is the only signal available.

nameison the vendor
g<n>A fan-out wire — one producer feeding two or more consumers.BoxTreeDemux, keyed by VarId. 573 of them in one real ladder project.
m<n>A multi-output assignment — one item driving several coils.A single BoxTreeAssign with several OutputItems. 40 in the same project, one of them a twenty-target rung.
i<n>An opaque leaf — one inVariable whose text is not a single safe token.One BoxTreeOperand, whose text stays text.
en<n>An enable echo — a box's ENO, which downstream boxes chain off.The box's En/Eno properties.
flowchart LR subgraph fanout["g<n> — one producer, two consumers"] a1([a]) --> AND1["AND"] b1([b]) --> AND1 AND1 --> D{{"Demux g1"}} D --> o1["out"] D --> o2["out2"] end subgraph multi["m<n> — one ASSIGN, two coils"] a2([a]) --> OR1["OR"] b2([b]) --> OR1 OR1 --> AS["Assign m1"] AS --> c1["out1 :=" ] AS --> c2["out2 S="] end

Two items on the left (a box and a demux) against one on the right (a box and one assign with two outputs). They spell nearly the same lines, which is the entire reason the prefixes differ.

g and m were one name once, and it cost fidelity in both directions. A real Demux feeding N assigns and a real multi-output assign spell identical lines, so every multi-output assign came back a Demux — a rung the engineer drew as one item with twenty coils round-tripped into twenty-one items. Neither driver could do better than guess and they guessed opposite ways: TwinCAT folded every g into one item (flattening real wires), CODESYS built a Demux for every one (inflating real items). Both shapes are ordinary in the same project, so a format that cannot tell them apart has to guess.

The m fold is conditional: the name is folded only when every use is the whole right-hand side of a top-level single-target assignment. A name used anywhere else is not the shape the writer mints, and falls through to the ordinary wire/inline rules rather than being forced into a fold that would drop a reference.

Statement forms

Wire definition — LET name := producer

LET g1 := (a AND b);
out  := g1;
out2 := g1;

Sink — lvalue := operand

A bare assignment (no LET) is an outVariable or coil. The coil KIND is the operator.

out  := (a AND b);
done := t1.Q;
latch S= trigger;       // a set coil
latch R= clear;         // a reset coil

Modifiers — they ride on the consumer

NOT (negation, leading) and RISING/FALLING (edge, trailing). A modifier rides on the operand or sink that consumes the wire, never as a statement of its own. 

out := NOT (a AND b);     -- negation on a sink's source
out := clk RISING;        -- rising edge
out := NOT g1;            -- NOT a separate `LET g2 := NOT g1;`

A modifier on a bare leaf inside a group turns that leaf into an opaque leaf, because NOT b is no longer a single token: out := (a AND NOT b) reads back as LET i1 := NOT b; out := (a AND i1);.

Coil storage — it is the assignment operator

A coil's kind is spelled by the operator, using ExST's own:

out := v;                 -- a plain coil
out S= v;                 -- a set coil
out R= v;                 -- a reset coil

Storage is a property of the coil, so it is written on the coil. It used to be a trailing word on the value (out := v SET;), which read backwards and cost three things:

  • A whole translation layer existed only to move the flag off the target on read and back on write, because both vendors keep it on the target.
  • A fan-out whose coils disagree could not be spelled at all — one trailing word had to serve every target of the statement, so only the first coil's storage survived. Per target it is just three lines: 
    LET m1 := (a OR b);
plain   := m1;
latched S= m1;
cleared R= m1;
  • A RESET coil came out as a SET coil. The vendors spell a reset coil Negation + Set on the target — one enum in two bits, not two modifiers — and the writer rendered no modifier on a target at all. GeneralProgramFlags network 0, comment "Always Off", pulled as AlwaysOff := AlwaysOff SET;. Pushed back, the flag that must stay false latches true.

S= and R= are recognised only as a token of their own — preceded by whitespace and not followed by = — so a comparison, or an l-value whose name ends in those letters, is never mistaken for one.

Operator group

Fully parenthesised, one operator kind per group, nestable. No precedence.

out := (a AND b);            -- a two-input box
out := (a AND b AND c);      -- the SAME operator repeated: ONE three-input box
out := ((a AND b) OR c);     -- nested: two boxes

Repeating one operator inside a group is an N-ary box, not a chain of two-input ones — which is what the engineer drew. Mixing kinds in one group ((a AND b OR c)) is NETWORK_BAD_EXPRESSION: the writer always fully parenthesises, so each group is exactly one operator.

Function call

out := MAX(a, b);
out := LIMIT(lo, x, hi);

It may also stand alone as a statement, when the box's output is connected to nothing — an ordinary shape in a ladder, and 34 of one real project's 373 networks: 

MOVE(g0, iDec);

FB instance call, and output reads

A function-block instance is always named (it is stateful) and called as a bare statement; its outputs are read elsewhere as inst.Pin. 

t1(IN := a, PT := pt);
done := t1.Q;
et   := t1.ET;

The one instance that carries its own type

A call names ONE thing and the push recovers the other from the declaration: t1(IN := a) plus t1 : TON; one line up is the type. ??? is the exception. It is the IDE's own marker for a call box whose instance has not been named — real content, drawn so the engineer sees the compile error — and it is declared nowhere. The box still has a type, so the type is written inline, in ST's own name : TYPE form: 

??? : L_TT1P_FlexCamBase(xEnable := , Axis := );

Four such boxes were measured in one real project. Without the inline type the type was dropped on pull and could not be recovered on push, so those POUs could be pulled and never pushed back.

EN/ENO

A box with a wired enable renders as an IF. en is the box's enable echo, so a downstream box chains off it. Three result shapes: 

LET en1 := a;
IF en1 THEN out := (b AND c); END_IF       -- into a SINK: one unmodified output

LET en2 := en1;
IF en2 THEN LET g1 := (b OR c); END_IF     -- into a NAMED wire: the result fans out
out  := g1;
out3 := g1;

LET en3 := a;
IF en3 THEN t1(IN := x, PT := pt); END_IF  -- gating an FB CALL
done := t1.Q;
The enable comes from the vendor's En pin, not from its EnEno flag. Measured in a real project, EnEno is true on all 1,256 boxes including every plain AND/OR, because it marks that the box supports EN/ENO. Keying on it would wrap every operator in the project in an IF.

Execute box — ST inside FBD/LD

A CODESYS Execute box is an EN/ENO block whose "call" is raw Structured Text. Its enable is not special — it reuses the ordinary EN/ENO wire and IF. The only new token pair is EXECUTE … END_EXECUTE around the verbatim ST, which may be arbitrarily complex: 

LET en1 := bRun;
IF en1 THEN
EXECUTE
IF bStart THEN
	target := 40 + 2;   (* the box's own ST, kept byte-for-byte *)
END_IF
END_EXECUTE
END_IF

A box with no wired EN renders as a bare EXECUTE … END_EXECUTE. The explicit END_EXECUTE delimiter — rather than "until END_IF" — is what disambiguates the ST's own nested END_IFs. The LSP should treat the span as full ST, not as this grammar.

Box output pins

A box has output pins of its own, wired to variables. The vendor names them, index-aligned with the slots, and the name decides the spelling — which is IEC's own split, not a Volt convention: a function's RESULT is assigned, its VAR_OUTPUTs use =>. 

dst := MOVE(src);                          -- the UNNAMED pin: the box's result
fc_MeanValue(20, oMeanValue => measured);  -- a NAMED pin
dst := f(src, oErr => err);                -- both on one box

An enabled box writes its own pin inside the IF, and the rung continues on the enable echo:

LET en1 := (g0 AND CopyMeasuredToDark);
IF en1 THEN DarkValue := MOVE(MeasuredValue); END_IF
CopyMeasuredToDark R= en1;

Output pins did not exist in an earlier model and were simply dropped: a box whose output was wired to TempI materialized without it, and TempI was nowhere in the file. 208 wired output pins on 171 boxes across 373 networks. The push side knew — it refused any box carrying outputs, because "network text has no form for them", which was true, and is what this form exists to end.

Two rules keep it honest, and both refuse rather than guess (NETWORK_UNSUPPORTED):

  • An infix operator has no argument list, so a named pin on one has nowhere to go. Operator boxes have unnamed outputs on every box measured, so this is a shape nobody has seen.
  • Two unnamed pins would be two results with one assignment to give. Every one of the 129 boxes with an unnamed output in a real project has exactly one.

An unwired pin is not written at all. A resolved FB box carries one slot per declared output whether or not the engineer connected it — 29 empty slots on one 30-pin box — and the ENO echo occupies slot 0 whenever the vendor names it so. Neither is a connection, so neither is spelled.

Opaque leaf — LET i := <text>

An inVariable whose text is not a single safe token — it has whitespace, parentheses or a call (a + 1, NOT x, DINT_TO_REAL(x)) — cannot sit at an operand position without mis-splitting, so it is named and gets its own statement. Its text stays text: parsing it like any other LET turns one leaf into a whole call box. 

LET i1 := NOT b;
out := (a AND i1);

Control flow

A jump target is a header field, not a statement. JMP and RETURN are flags on an assignment node, which is why a rung can drive a coil and a jump at once. 

NETWORK 3 LD LABEL: Retry
  IF fault THEN JMP Retry; END_IF
END_NETWORK

NETWORK 4 FBD
  IF done THEN RETURN; END_IF
  step := (step + 1);
END_NETWORK

The network header

NETWORK 0 FBD LABEL: myLabel TITLE: "optional title" DISABLED
  // a network comment                   -- optional, FIRST in the body
  out := (a AND b);
END_NETWORK

Index first, then the language, then the named optional fields in any order, then DISABLED. The index is verbatim and must be unique — it is the network's own identity, and two networks sharing one would collide in the IDE (NETWORK_DUPLICATE_NETWORK). A body may mix FBD and LD networks, vendor permitting.

A network's label comes before its comment, mirroring the IDE's own header layout (the label above the single comment box). The reader accepts them in either order — only the canonical form is fixed, and it is fixed this way so that writing a network the way the IDE displays it is not refused.

The gate

NetworkTextGate.Validate is the pre-write check, and it is pure — no IDE, no vendor, no document. Three steps, in order:

  1. Language. The NETWORK marker names FBD or LD. An unknown language is refused here with a clear message, rather than downstream as a misleading "not writable".
  2. Parse. The body is structurally valid network text.
  3. Canonical form. The parser is the exact inverse of the writer, so a body that does not re-emit identically is not canonical — it would drift on the next pull, or silently rename a wire. The diagnostic returns the canonical text to paste, and the line where it first differs.
Two earlier checks are gone, because the transport no longer needs them. The PLCopen convergence gate required a body to reach a fixed point through a writer/reader pair; it existed because the body was regenerated from a projection on every write. Nothing is regenerated now — CODESYS mutates the live objects and TwinCAT rewrites only the networks that changed — so there is no loop to converge. The leaf fan-out refusal rejected a leaf read more than once in a network, because TwinCAT's importer crashed on a shared one; that shape was expressible only in a graph, and a tree cannot share a node, so it is now unrepresentable rather than refused. That is the clearest single case of a model change removing a class of bug instead of guarding it.

Shapes with no text form

Some bodies cannot be written as network text at all. These are not diagnostics — nothing is refused and no push is involved. The body materializes as a marker instead, so the file says what it is and the POU is read-only until the engineer changes the shape: 

(* @volt-graphical: LD (rising-edge coil) *)

All three used to render as a plain :=, which is the same silent inversion the reset coil suffered, and just as invisible: re-emitting the text reproduces it byte-for-byte.
rising-edge coil
falling-edge coil
a multi-target rung

The control-flow path renders one destination and drops every other target; the assignment path renders the coils and has no form for the jump. Between them, a coil the engineer can see in their IDE was simply absent from the pulled file — with the fixed point hiding it, because the text round-trips to itself and nothing ever asks where the coil went.
No syntax was invented for the three coil kinds, and that is a measurement, not caution. A census of every assignment target in five real customer projects — 576 targets, 48 graphical POUs, 427 networks, including a 34-ladder project — found zero of them. If one ever turns up in a real body, that census is what a spelling should be designed from. A spelling for the fourth shape is possible too (a target operator beside S=/R=) and is deliberately not guessed at: whether it occurs in real projects is a question only an archive census can answer, and the corpora on disk are pulled text, which — being written by the code above — cannot show the coil it dropped.

The boundary on the fourth is the TARGET COUNT, not the mixture: a lone jump, a lone return and an ordinary fan-out of plain coils all spell fine. A guard that refused every control-flow target would have turned a working ladder POU into a marker.

Diagnostics

Every refusal carries a stable code, a 1-based line and a message. On the wire they arrive as PushConflict.code / .line; the CLI prints name:line [CODE] message.

coderaised when
NETWORK_NOT_CANONICALIt parses, but does not re-emit identically — it would drift on the next pull. The message carries the exact canonical form.
NETWORK_PARSEAny other structural error: a statement before any network, an unexpected END_NETWORK, a leftover legacy VAR_TEMP/END_VAR line, or a bare myLabel: line (the message names the header field it moved to).
NETWORK_NOT_CLOSEDA NETWORK block is missing its END_NETWORK.
NETWORK_DUPLICATE_NETWORKA network index appears more than once. Their ids would collide and the IDE would merge or corrupt them.
NETWORK_DUPLICATE_NAMEA wire, result or instance name is defined twice in one network. A name introduced with LET is its definition, and two definitions have no single meaning.
NETWORK_BAD_EXPRESSIONA malformed group: partial or unbalanced parens ((a AND b) OR c), mixed operators in one group ((a AND b OR c)), or an operator with no right-hand operand.
NETWORK_UNKNOWN_OPERATORThe symbol is not in the operator table above.
NETWORK_UNSUPPORTEDRaised by the writer, not the parser: a body whose shape has no spelling — an operator box naming an output pin (the infix form has nowhere to put it), or a box with two unnamed output pins (there is one assignment to give). Both are refused rather than resolved by dropping a pin.

Worked examples

-- 1. Simple operator (single-use → inlined)
NETWORK 0 FBD
  out := (a AND b);
END_NETWORK

-- 2. Nested, fully parenthesised
NETWORK 0 FBD
  out := ((a AND b) OR c);
END_NETWORK

-- 3. Fan-out: one producer, two consumers → a g-wire
NETWORK 0 FBD
  LET g1 := (a AND b);
  out  := g1;
  out2 := g1;
END_NETWORK

-- 4. One item driving several coils, whose kinds disagree → an m-assign
NETWORK 0 LD
  LET m1 := (a OR b);
  out1 := m1;
  out2 S= m1;
END_NETWORK

-- 5. Opaque leaf: a negated operand cannot inline
NETWORK 0 FBD
  LET i1 := NOT b;
  out := (a AND i1);
END_NETWORK

-- 6. EN/ENO into a sink
NETWORK 0 FBD
  LET en1 := a;
  IF en1 THEN out := (b AND c); END_IF
END_NETWORK

-- 7. Timer FB: instance call + output reads
NETWORK 0 FBD
  t1(IN := start, PT := pt);
  done := t1.Q;
  et   := t1.ET;
END_NETWORK

-- 8. Ladder: a parallel branch (OR) and a series (AND) on one rung
NETWORK 0 LD
  out := ((a OR b) AND c);
END_NETWORK

-- 9. A titled, disabled network
NETWORK 7 LD TITLE: "Commissioning only" DISABLED
  bypass := TRUE;
END_NETWORK

-- 10. Variable feedback (the fed-back read is a leaf, not a graph cycle)
NETWORK 0 FBD
  iCount := (1 + iCount);
END_NETWORK

Type inference — the LSP's job

Network text does not write wire types. A LET wire has no annotation and the bridge needs none. For hover, completion and type-checking, the LSP infers a wire's type from its defining expression and the POU declaration:

producerinferred type
AND / OR / XORBOOL

+ - * / MODThe operands' common result type.
FN(…)The function's declared return type.

a literalThe literal's own type.

The declaration is the authority for real variables. The LSP has the whole POU document — declaration and body — so it resolves names to their VAR types and propagates through expressions. The bridge's parser deliberately does not: it only needs the wire/sink shape, which LET gives it directly.

The LET-vs-bare distinction is also a binding signal. A LET name is a single-assignment local scoped to its network; a bare l-value is a write to a declared variable. Treat them differently for go-to-definition and rename.

Implementing a language server over it

The format is small and regular. Concrete targets per feature:

  • Semantic tokens. Distinct classes for keywords, operators, modifier words, wire names (a LET binding), sinks (a bare l-value), FB instances, literals and comments. Colouring wires, sinks and instances differently is what makes a network instantly legible.
  • Folding and symbols. Each NETWORK … END_NETWORK is a region; its index plus its optional label is the symbol name. EN/ENO IF blocks fold too.
  • Hover. A wire → its inferred type and defining expression; a variable → its declared type from the POU's VAR; an FB instance → its type and pin signature.
  • Completion. Declared variables and instances, FB pin names inside inst(… := …), operators, function names, keywords.
  • Diagnostics. Surface the structural codes above as you type, so a push is never refused — plus the code-correctness checks the bridge does not do.
  • Definitions and references. A LET wire ↔ its uses (network-scoped, single-assignment); a variable ↔ its declaration; a JMP ↔ its label; an inst.Pin ↔ the call.
  • Rename. A LET wire is safe to rename within its network. Renaming a real variable is a declaration-level rename.
