Items & kinds

What a project is made of, what each thing is called on the wire, and which file it becomes. One table, generated from ItemKind — the single source of truth both drivers classify onto.

The model

A project is a tree. A walk flattens it into items, each with a name, a kind code and a folder path. Not every node becomes an item: some are recursed through, some are inlined into their parent, and some are skipped outright.

a node is…and then
emittedIt is an item on the wire, with a version, and it materializes as a file.
a folderIt becomes a path SEGMENT on the items beneath it. Folders are never items and have no file.
a container managerA library / recipe / visualization manager: pure grouping, no content of its own. Recursed exactly like a folder, so a library materializes at Library Manager/<lib>/<lib>.library with no stub beside the folder.
inlined in a POUA method, action, property, accessor or transition. It travels inside its POU's single file, as a block the ST layer renders and parses back.
a recurse-only containerCODESYS's Application / PlcLogic / Device / Task Configuration, and any node carrying no specific object type. Walked through, never emitted.
skippedTransient and hidden objects, and CODESYS's own IUnknownObject "no plugin loaded" marker.

Names, kinds and extensions

The item NAME is the identity, and on the wire it is full — name.kind. IEC guarantees unique names within a kind, not across them: a control module and the visualization that draws it are CM_Carrier.fb and CM_Carrier.visualization, and a real customer project ships two such pairs. Collapsed onto one bare slot, the walk order picked a winner — the FB's version was invisible to the aggregate hash, and the push's ifVersion gate answered with the visualization's hash, which meant the FB could be pulled and never pushed back.

Do not add a duplicate-name guard that throws. Real projects legitimately repeat names across kinds, and throwing breaks refs. The fix is to key the wire's maps by the identity the wire already publishes.

Below the vendor seam the same item is addressed by its bare name — the IDE's own lookup key, which has no extension. Every version and folder map Volt publishes is keyed by the full name and derived in one place; an item that could not be materialized has no full name and keeps its bare one there.

A file's extension carries the kind and nothing else. A body's language is not in the extension: an editable FBD/LD body is the same .fb/.prg/.fun as a textual one — the language rides on the body's IMPLEMENTATION line in the content, IMPLEMENTATION ST, IMPLEMENTATION FBD or IMPLEMENTATION LD — and a CFC/SFC/IL body is that kind's extension too, materialized as its line IMPLEMENTATION CFC UNSUPPORTED (and so on) with no implementation under it.

The DUT: four codes, one kind, five wire names

A DUT is one item kind inside the engine (dut). TwinCAT stores four tree codes for it (605 enum / 606 struct / 607 union, and 623 alias); CODESYS classifies every IDUTObject onto one and creates with one call. All of them map to dut.

On the wire and on disk it is named by its subtype as its vendor states it — X.struct / X.enum / X.union / X.alias. The driver hands the vendor's answer up with the item's content (ItemContent.DutSubtype), and the one place a full wire name is minted (Materializer.FullWireName) spells it; the engine never reads a DUT's text for it. Never from the tree code either: TwinCAT's code lags an in-place change (DIALECT C2e). A DUT whose vendor states no subtype is published as X.dut — the one fallback: tracked, pulled and pushed like the other four, never unreadable for want of a subtype and never named by a guess. The file name is the wire name: no client maps one extension to another.

Interim (openspec push-without-header-check, steps 5.C/5.D): until CODESYS answers from its precompile signature and TwinCAT from its own classifier, both drivers answer through the engine's old text reader, which states nothing where it used to refuse. A library's DUTs are still named by that reader until step 5.D.2 takes them from the library signature's flags.

Below the vendor seam the four names are one object, the bare name X. So a subtype change — a struct rewritten as an enum — is one update of that object, never a delete plus a create: the push decides it, whichever shape git gave the change. See the push rule.

This row used to read "not used by Volt". 605/606/607 were therefore unmapped, so every DUT authored in the TwinCAT IDE — the ordinary case — was invisible to refs and fetch. Absent means deleted to a pull.

Upgrading a workspace from .dut

A Volt from before the subtype reached the wire named every DUT X.dut, and a workspace's baseline (.git/volt/ide-refs.json) is keyed by wire name. After upgrading, run volt pull once; if a command refuses the baseline by name, delete .git/volt/ide-refs.json and pull. An old X.dut key is not refused: .dut is a wire name again (a DUT whose vendor states no subtype), so the two cannot be told apart. That is safe — an update quoting the version such a key holds reaches the live DUT only if it equals that DUT's content version, and the pull renames the key to the name the IDE publishes. There is no translation of old keys.

Most files keep their names — not all. The previous Volt already wrote DUT files as .struct / .enum / .union / .alias, but its subtype reader was looser than the one that now names the wire, and a DUT it read differently comes back from the recovery pull under a new name. It matched the body keyword as a prefix, and it looked for trivia only at the start of a line: a block comment there was stepped over, but a pragma there took the whole line with it, code and all. So any comment or pragma between the type's colon and its body token was read AS the body token (a block comment's (* as an enumeration's (, anything else as an alias), a colon inside a comment was taken for the type's own, and a pragma that starts the TYPE line dropped the type's colon, so a member's colon (a : INT;, or an initializer's :=) stood in for it — or none was found — and the answer was alias. The current reader matches whole tokens and steps over every comment and pragma, keeping the code beside it. The shapes that move:

declarationwasis now
TYPE T : Struct_Alarm; — an alias of a type whose name begins with STRUCT or UNIONT.structT.alias
TYPE S : // note, then STRUCT on the next lineS.aliasS.struct
TYPE S : (* note *) STRUCT — a block comment before the bodyS.enumS.struct
TYPE T : (* note *) INT (0..10); — a block comment before an alias's typeT.enumT.alias
TYPE E : {attribute 'strict'} (A, B); — a pragma before an enumerationE.aliasE.enum

The same holds for UNION behind a comment, and for a pragma that starts the body's own line (TYPE E :, then {attribute 'strict'} (A, B);) — the previous reader dropped that whole line and read the END_TYPE after it as an alias. The pull shows such a DUT as a rename the engineer did not make: the old name is gone from the IDE, so it is removed, and the new one is written. Nothing is lost — a local edit to the old file follows it through git's rename detection in the merge.

A declaration the vendor gives no subtype was X.alias; it is now X.dut. That covers no colon at all (TYPE X END_TYPE), a colon with no type (TYPE X : ;), and an unclosed comment that swallows the body. The pull shows it as a rename of its file to X.dut (the old name removed), and every push of it is an ordinary one — no --force. When the declaration says what it is, the next pull renames the file to the subtype; a push of X.dut over a DUT the IDE now names X.enum reaches it by the version it quotes (the push rule). The same happens outside an upgrade: a subtype change typed in the IDE passes through a moment with no subtype, and a pull taken then is an ordinary one.

Source, addressable, writable — three different questions

flagasks
ST sourceIs this assembled Structured Text? The LSP parses it; volt init colours it; it is in the four SOURCE_EXTENSIONS manifests.
addressableDoes the wire address it BY NAME at top level? Every source kind, plus the writable reference kinds.
a push may write itCan a push send it back? True for every source kind — and for .task, which is writable without being source.

Conflating writable with source is what kept the third column from existing. A .task is not structured text, the LSP must not parse it as such — yet its fields are perfectly writable on the vendor, every one a setter measured live.

Write support that differs per vendor

Almost everything is symmetric — the wire is the parity boundary, and both vendors answer identically. The exceptions are listed here, because "can I edit this file?" is the question this page exists to answer and the generated table below cannot carry it.

kindCODESYSTwinCATwhy
task writable writable Both, by routes that share nothing below the format. CODESYS has a live setter per field. TwinCAT assembles the same six fields from two tree items — the PLC task's linked SYSTEM task carries priority and cycle time, the ordered calls are the PLC item's own children — and reads every write back, because that vendor accepts a schedule it has no intention of applying. Three fields have no TwinCAT counterpart (a non-cyclic type, an event, a watchdog) and are refused rather than dropped.

Which vendor implements which writable kind is declared and gated (test/Volt.Repo.Gates/VendorCapabilityParityTests.cs), so a future one-sided kind cannot arrive unnoticed — and the vendor that lacks a capability has to refuse with UNSUPPORTED rather than accept and do nothing, which is the failure mode a capability gap actually produces in the field.

The kind table

Codes, kinds, file extensions and every predicate, read off the same class the walk uses. A row exists because a constant does.

Workspace file extensions

The registry scripts/check-wiring.ts cross-checks every other runtime's copy against — the C# engine, the LSP, volt-control, and four separate places in the VS Code manifest — so a new source kind cannot be added in one place and silently missed in another.

dut is the engine's kind, not an extension: it names no file and no wire item (both carry the subtype). A DUT's four extensions are ordinary rows here, each mapping to that kind.

How each vendor classifies

TwinCAT — a numeric enum

The codes are TwinCAT's own TREEITEMTYPE (the PLC range), which is why each C# constant is the PascalCase of its official name. The numbers in the table are the live build's, not the published documentation's: Beckhoff renumbered 622/624/625 into the 650s, and 628/629/631/632/633/657 are observed live with no published name at all. Catalogue notes go stale; these were measured.

Codes in the PLC range that are not in the table are genuinely unknown — never seen live, not in the published enum. An unmapped code drops the item from the walk, which is not a theoretical cost: that is exactly what happened to every TwinCAT-authored DUT while 605–607 were missing.

To close one: open a project that has the object (persistent GVLs, a parameter manager, CNC/NC, cam or image pools), walk the tree and read the raw TREEITEMTYPE off it. Anything a walk cannot classify is logged as unmapped-kind at Debug with its number — see the drop tallies.

CODESYS — by interface

CODESYS has no numeric enum; it classifies by which IObject interfaces a node carries, onto the same constants. IPOUObject → program/function/function block (refined from the declaration), IDUTObject → dut, IGVLObject/INVLObject → gvl, IInterfaceObject → interface, and so on down a fixed order. The order matters — several nodes carry more than one interface.

A node with no specific object type — only the base IGenericObject/IObject — is treated as a transparent grouping container and recursed into, so nested source is never dropped. That is how SoftMotion's "Kinematics" group and the drive "Functions" group behave.

The order is fixed and it matters: several nodes carry more than one of these, and the first match wins.

Both drivers emit identical wire kinds, so an item hashes identically regardless of which IDE it came from. That is the whole point of a shared code table: parity is a property of the data, not of two implementations agreeing by hand.
