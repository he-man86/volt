Items & kinds

What a project is made of, what each thing is called on the wire, and which file it becomes. One table, generated from ItemKind — the single source of truth both drivers classify onto.

The model

A project is a tree. A walk flattens it into items, each with a name, a kind code and a folder path. Not every node becomes an item: some are recursed through, some are inlined into their parent, and some are skipped outright.

a node is…and then
emittedIt is an item on the wire, with a version, and it materializes as a file.
a folderIt becomes a path SEGMENT on the items beneath it. Folders are never items and have no file.
a container managerA library / recipe / visualization manager: pure grouping, no content of its own. Recursed exactly like a folder, so a library materializes at Library Manager/<lib>/<lib>.library with no stub beside the folder.
inlined in a POUA method, action, property, accessor or transition. It travels inside its POU's single file, as a block the ST layer renders and parses back.
a recurse-only containerCODESYS's Application / PlcLogic / Device / Task Configuration, and any node carrying no specific object type. Walked through, never emitted.
skippedTransient and hidden objects, and CODESYS's own IUnknownObject "no plugin loaded" marker.

Names, kinds and extensions

The item NAME is the identity, and on the wire it is full — name.kind. IEC guarantees unique names within a kind, not across them: a control module and the visualization that draws it are CM_Carrier.pou and CM_Carrier.visualization, and a real customer project ships two such pairs. Collapsed onto one bare slot, the walk order picked a winner — the FB's version was invisible to the aggregate hash, and the push's ifVersion gate answered with the visualization's hash, which meant the FB could be pulled and never pushed back.

Do not add a duplicate-name guard that throws. Real projects legitimately repeat names across kinds, and throwing breaks refs. The fix is to key the wire's maps by the identity the wire already publishes.

Below the vendor seam the same item is addressed by its bare name — the IDE's own lookup key, which has no extension. Every version and folder map Volt publishes is keyed by the full name and derived in one place; an item that could not be materialized has no full name and keeps its bare one there.

A file's extension carries the kind — what the IDE stores per object, its class — and nothing else. A body's language is not in the extension: an editable FBD/LD body is the same .pou as a textual one — the language rides on the body's IMPLEMENTATION line in the content, IMPLEMENTATION ST, IMPLEMENTATION FBD or IMPLEMENTATION LD — and a CFC/SFC/IL body is that kind's extension too, materialized as its line IMPLEMENTATION CFC UNSUPPORTED (and so on) with no implementation under it.

The POU: one class, one kind, one wire name

A program, a function block and a function are one item kind, pou, published, stored, pushed and analysed as X.pou on both vendors. Whether a POU is a PROGRAM, a FUNCTION_BLOCK or a FUNCTION is decided by its text on both: CODESYS has one POUObject class whose kind follows its declaration, and TwinCAT's three tree codes (602 / 603 / 604) lag an in-place write and are re-derived from the text on a reload (DIALECT C2f, C2g, C2h). An extension carries only what the IDE stores per object, so nothing in Volt reads which of the three a POU is — the IDE and its build own it, and the LSP reads it from the text as analysis. A PROGRAM rewritten as a FUNCTION_BLOCK is an ordinary content update of X.pou.

The file's outer END line mirrors its own header: PROGRAM closes with END_PROGRAM, FUNCTION_BLOCK with END_FUNCTION_BLOCK, FUNCTION with END_FUNCTION — the keyword read with comments, strings and pragmas skipped. A declaration that opens with none of the three (an empty or prose text, a NAMESPACE) has no END line its text can mirror, and Volt invents none: the pull lists the item unreadable by name (16,990 of 16,990 corpus POUs open with one of the three, so this meets only a text mid-edit in the IDE). It closed with END_FUNCTION_BLOCK until openspec bridge-one-to-one — a line the IDE does not hold. A push creates a POU as a function block — or as the class its %CLASS line names — and writes its declaration before its members, so the IDE judges each member against the text that was sent (DIALECT C2k). A member's kind is its class too, and a member whose text opens with another keyword than its class's is refused on pull by name (C2l). (openspec push-without-header-check 5.Q — until then the wire named a POU X.prg / X.fb / X.fun from its text. Those names are no extension any more: a workspace that still holds such files sees them as foreign files and X.pou as added on its next pull, and a baseline keyed by them is refused by name — delete .git/volt/ide-refs.json and pull.)

The DUT: four codes, one kind, one wire name

A DUT is one item kind inside the engine (dut). TwinCAT stores four tree codes for it (605 enum / 606 struct / 607 union, and 623 alias) and creates every DUT on the 606 seed, which a reload re-derives from the text (measured: tc-dut-create-reload, DIALECT C2e); CODESYS classifies every IDUTObject onto it and creates with one call. A CODESYS text-list enumeration (ITextListEnumerationObject) is a dut too, but another class: it pulls with %CLASS TEXTLIST_ENUM and a create makes that class through the vendor's own factory — its text-list rows are rebuilt from the declaration on every write (a measured cache, textlist-enum-edit, DIALECT C2r). It used to be folded onto a plain DUT, and a push re-created it as one.

On the wire and on disk every DUT is X.dut, whatever its shape — struct, enumeration, union or alias, a library's DUT included. The name is a pure function of the kind, so naming a DUT reads no text and asks for no vendor parse; nothing in Volt decides a DUT's subtype (the IDE and its build own it, and the LSP reads the shape from the text as analysis). A struct rewritten as an enum is therefore an ordinary content update of X.dut: no rename, no special push rule. The file name is the wire name: no client maps one extension to another. (openspec push-without-header-check 5.P — until then the wire named a DUT by its subtype, X.struct and so on. Those names are no extension any more: a workspace that still holds such files sees them as foreign files and X.dut as added on its next pull, and a baseline keyed by them is refused by name — delete .git/volt/ide-refs.json and pull.)

This row used to read "not used by Volt". 605/606/607 were therefore unmapped, so every DUT authored in the TwinCAT IDE — the ordinary case — was invisible to refs and fetch. Absent means deleted to a pull.

Object properties: the %-lines

Volt's text is the vendor's object, one to one (openspec bridge-one-to-one): every member of an object that is not its text is spelled, a measured editor cache, or refused by name — nothing folded, guessed or defaulted. The members a declaration and a body cannot hold — the object's class where the text cannot tell it, its build properties, its comment, its network-variable settings, its file link — travel as %-lines, the directive form %FOLDER already was. Each is a field of one closed, typed record, ObjectProperties, required on ItemContent and on every Member, so a driver that has not read an object's properties cannot build its content. The examples below are the writer's own output.

  • What is a property line: only % followed by one of the keys above, the key ending at a space or the line's end. Every other line that opens with % is code — a direct-address assignment %QB1 := x; can stand exactly where properties are read.
  • Order: %CLASS first, then a member's %FOLDER, then the table's order; each key once, except %UNDEFINE and %NETVAR, which repeat in the vendor's order. The writer emits exactly that, and the reader refuses another order, a repeated key, a value on a flag and a valued key with none — naming the key and the line. The LSP's format layer (frontend/syntax/format/object-properties.ts) reads the same list and reports the same.
  • Placement: directly under the object's IMPLEMENTATION line, or — for an object with no body (a DUT, a GVL, an interface, a property, an IMPLEMENTATION NONE member) — closing its declaration.
  • Absence is the value measured on every object without that vendor property (false, 0, empty). The read still requires the vendor member wherever the vendor archives it: a missing one refuses the item by name.
  • A vendor member no key names refuses the item on pull — listed unreadable with the member's name — rather than pulling it without the member. A POU image (POUImageProperty) is the one named exception: a binary with no text form, warned in the pull report and never written.
  • Vendors: CODESYS READS every key. It WRITES the build keys and %COMMENT; a change to %NETVAR, %PARAMETER_LIST or %FILE_LINK — the line added, removed or edited, on an existing object or a new one — is refused by name before anything of the push lands (no measured write: 1, 0 and 1 occurrence in the corpora, niche: accepted loss). Change it in the IDE and pull; the line round-trips unchanged. %CLASS is never changed in place (below). TwinCAT has no measured member for any key: a push carrying one is refused by name, and a pull of an item with a .plcproj build entry other than SubType (or an <ObjectProperties> other than an SFC body's) is refused by name, until a measurement says what it is.
  • Migration: a re-pull adds the lines to the files that carry such properties. A text written before them would push "not excluded" over an excluded object, so the binding records the text-format version and a push from an older workspace is refused: re-pull: the text predates object properties.

Classes are made at the create, never changed in place (C2l: a CODESYS object's class does not change). CODESYS makes a check function (%CLASS CHECK <check>) and a text-list enumeration through the vendor's own paths, and a METHOD ABSTRACT with no code as its abstract-method class; a receiving NVL (only the vendor's wizard makes one), a persistent list, a sending GVL (%NETVAR) and a parameter list (%PARAMETER_LIST) are refused as a create, by name. An existing one is updated — its declaration and its build keys and comment written — while a change to its %NETVAR or %PARAMETER_LIST line is refused, as above. TwinCAT's automation interface makes no special class, so every %CLASS create there is refused by name (C2s). A member renamed in a push keeps its object — the vendor's rename, GUID and class kept — when exactly one member of that kind was dropped and one added; a member whose kind changes under the same name is refused, the remedy (two pushes) stated.

Source, addressable, writable — three different questions

flagasks
ST sourceIs this assembled Structured Text? The LSP parses it; volt init colours it; it is in the four SOURCE_EXTENSIONS manifests.
addressableDoes the wire address it BY NAME at top level? Every source kind, plus the writable reference kinds.
a push may write itCan a push send it back? True for every source kind — and for .task, which is writable without being source.

Conflating writable with source is what kept the third column from existing. A .task is not structured text, the LSP must not parse it as such — yet its fields are perfectly writable on the vendor, every one a setter measured live.

Write support that differs per vendor

The wire is the parity boundary: the same object gives the same text on both vendors — gated offline by both drivers' doubles (test/shared/WireParityCases.cs: stub manifests, library references, interface accessors) and live by test/e2e/vendor-parity.test.ts. What one vendor cannot hold it refuses by name; it never writes it as something else. Those refusals are listed here, because "can I edit this file?" is the question this page exists to answer and the generated table below cannot carry it.

Which vendor implements which writable kind is declared and gated (test/Volt.Repo.Gates/VendorCapabilityParityTests.cs), so a future one-sided kind cannot arrive unnoticed — and the vendor that lacks a capability has to refuse with UNSUPPORTED rather than accept and do nothing, which is the failure mode a capability gap actually produces in the field.

The kind table

Codes, kinds, file extensions and every predicate, read off the same class the walk uses. A row exists because a constant does.

Workspace file extensions

The registry scripts/check-wiring.ts cross-checks every other runtime's copy against — the C# engine, the LSP, volt-control, and four separate places in the VS Code manifest — so a new source kind cannot be added in one place and silently missed in another.

Every kind has exactly one extension; a DUT's is dut, whatever its shape.

How each vendor classifies

TwinCAT — a numeric enum

The codes are TwinCAT's own TREEITEMTYPE (the PLC range), which is why each C# constant is the PascalCase of its official name. The numbers in the table are the live build's, not the published documentation's: Beckhoff renumbered 622/624/625 into the 650s, and 628/629/631/632/633/657 are observed live with no published name at all. Catalogue notes go stale; these were measured.

Codes in the PLC range that are not in the table are genuinely unknown — never seen live, not in the published enum. An unmapped code drops the item from the walk, which is not a theoretical cost: that is exactly what happened to every TwinCAT-authored DUT while 605–607 were missing.

To close one: open a project that has the object (persistent GVLs, a parameter manager, CNC/NC, cam or image pools), walk the tree and read the raw TREEITEMTYPE off it. Anything a walk cannot classify is logged as unmapped-kind at Debug with its number — see the drop tallies.

CODESYS — by interface

CODESYS has no numeric enum; it classifies by which IObject interfaces a node carries, onto the same constants. IPOUObject → program/function/function block (refined from the declaration), IDUTObject → dut, IGVLObject/INVLObject → gvl, IInterfaceObject → interface, and so on down a fixed order. The order matters — several nodes carry more than one interface.

A node with no specific object type — only the base IGenericObject/IObject — is treated as a transparent grouping container and recursed into, so nested source is never dropped. That is how SoftMotion's "Kinematics" group and the drive "Functions" group behave.

The order is fixed and it matters: several nodes carry more than one of these, and the first match wins.

Both drivers emit identical wire kinds and — gated, not assumed — identical text for the same object, so an item hashes identically regardless of which IDE it came from. That is the whole point of a shared code table: parity is a property of the data, not of two implementations agreeing by hand. A kind with no descriptor reader (a visualization, a text list) is the one stub on both, the kind and a newline (ItemKind.EmptyManifest); TwinCAT wrote Name=<name> there until openspec bridge-one-to-one, so the same visualization hashed differently per vendor.
