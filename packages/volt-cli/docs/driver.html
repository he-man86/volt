The driver layer

IVendorDriver (Volt.Engine/Seam/) is the whole vendor seam: one interface, composed of three, and the only code in the system that knows what a CODESYS or a TwinCAT is. This is the layer to lift into another project if what you want is to drive a PLC IDE from your own program rather than to speak Volt's wire.

What it is

classDiagram class IVendorDriver { the one type a vendor implements } class IVendorSession { declaration · attach · threading · probe · build } class IVendorTree { walk · classify · create · delete · rename · move } class IVendorStore { read content · write content · manifests · pre-flight } IVendorDriver --|> IVendorSession IVendorDriver --|> IVendorTree IVendorDriver --|> IVendorStore

The three facets stay separate because they answer different questions and fail differently. A tree walk can skip a subtree it cannot enumerate; a content read cannot skip a body. Keeping them apart is what lets each read as a focused contract instead of one forty-member god interface.

The one rule that makes it reusable

IVendorStore speaks Content (kinds, languages and property keys the host declares), and nothing above the seam knows a vendor's own representation. A graphical body crosses as network text; the driver converts. Get that boundary right and everything above it is vendor-blind for free.

A vendor's file format is not part of the contract: an IDE with no PLCopen export (TIA Portal's Openness has its own representation) implements it as readily as CODESYS, which hands over its typed objects, or TwinCAT, which edits its own archive. A body's language arrives inside the content, never as a second question to the IDE.

Why HostWalk carries completeness

Both drivers skip a subtree they cannot enumerate rather than aborting the whole walk, which is right — a transient COM fault on one folder should not fail a pull. The sync layer derives deletions as "known to the client, absent from this walk", so a walk that does not say what it skipped reports every item beneath a faulting folder as deleted, and the pull removes the engineer's files for POUs still sitting in the IDE.

If you implement this interface, populate UnwalkedFolders. An entry means "there may be items under here that this walk did not see" — never "these are gone".

And one place where a default would cost data: the class at the create. IVendorTree.CreateChild takes the class the text names (CreateArgs.Class; null is the kind's plain class) — a CODESYS object's class never changes in place (DIALECT C2l), so a driver that cannot make the named class refuses the create by name (ChildRefusedException) rather than making the plain one. ValidateProperties is the pre-flight half: a property set this driver has no measured write for is refused before the first op lands.

Threading, and why it is on the interface

Both IDE automation surfaces are single-threaded-apartment. Every IDE-touching operation is marshalled through the host's MarshalToIdeThread<T>, bracketed by the session's RunOnStaThread<T>, and that is load-bearing rather than defensive: touching the object model off the IDE's own thread is how you get a hang that looks like a network problem.

The engine's session (Sync/ComposedSession) implements the parts that are identical across vendors — the degraded-state machine, the liveness bracketing around the marshal, the single-flight health probe, and the composition of the whole health response. A host supplies only primitives: its marshal, its probe (ProbeProjects: the rows, whether its binding is live, whether its IDE answered) and its probe floor. No host composes health's wire shape, so two vendors cannot answer it differently.

HandlesSurviveStructureChange is the other threading-adjacent fact worth knowing before you write a driver. On CODESYS a handle survives adding a child; on TwinCAT it does not, because a member is not a separate file there and placing one is a round trip through the enclosing POU's archive, which replaces the item. The push re-finds the item after each member it adds only where the host says handles do not survive.

The pre-flight

ValidateSource throws exactly what Write would throw, for the reasons this driver can decide without touching the IDE. The push calls it for every op before it applies the first one.

The engine's own pre-flight already covers everything decidable from the source text — a malformed document, network text that does not parse or is incomplete — and that is vendor-neutral by construction. What it cannot cover is a shape one vendor cannot express. Being pure is the whole point: called from inside the write, a push whose second item carried such a shape would leave the first item in the project and tell the caller it had failed.

VendorDriverBase refuses nothing by default, which is the honest answer for a driver whose refusals genuinely need the live objects. A pre-flight that guesses is worse than one that declines to.

The interface, member by member

Signatures, nullability and tuple element names exactly as the contract declares them — string? versus string is a rule an implementer has to honour.

Lifting this into another project

  1. Take Volt.Engine/Seam/, Volt.Engine/Ide/ and Volt.Engine/Item/. The contract and its registries, the vocabulary, and the shared helpers (ItemLookup, SourceScopes). No wire, no sync.
  2. Take one driver — Volt.Ide.Codesys or Volt.Ide.Twincat — as the worked example of what a vendor implementation costs.
  3. Decide whether you want Format/. If your project wants bodies as text, yes: that is the ST layer and network text. If it only wants structure, IVendorTree alone is coherent.
  4. Leave Sync/ and Volt.Wire behind unless you want Volt's versioning and push semantics too. They sit above the seam and assume a git-shaped client.

The dependency that is not optional is Volt.Contracts: the driver contract references ConnectRequest, HealthResponse and BridgeDiagnostic. It is netstandard2.0 with no framework dependency, deliberately, so it loads in an in-process net48 host without fighting the IDE's own assemblies.
