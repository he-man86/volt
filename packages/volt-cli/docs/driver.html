The driver layer

IIdeDriver is the whole vendor seam: one interface, composed of three, and the only code in the system that knows what a CODESYS or a TwinCAT is. This is the layer to lift into another project if what you want is to drive a PLC IDE from your own program rather than to speak Volt's wire.

What it is

classDiagram class IIdeDriver { the one type a vendor implements } class IIdeSession { attach · liveness · threading · build } class IProjectTree { walk · create · delete · rename · move } class ICodeStore { read content · write content · manifests } IIdeDriver --|> IIdeSession IIdeDriver --|> IProjectTree IIdeDriver --|> ICodeStore

The three facets stay separate because they answer different questions and fail differently. A tree walk can skip a subtree it cannot enumerate; a content read cannot skip a body. Keeping them apart is what lets each read as a focused contract instead of one forty-member god interface.

The one rule that makes it reusable

ICodeStore speaks ItemContent, and nothing above the seam knows a vendor's own representation. A graphical body crosses as network text; the driver converts. Get that boundary right and everything above it is vendor-blind for free.

This is not a style preference — it is the correction of a real design failure. The interface used to demand a PLCopen document: 

string  ReadXml(ItemRef item);              // "export this POU as PLCopen XML"
void    WriteXml(ItemRef item, string xml);
string? BodyLanguage(ItemRef item);

which made a vendor's file format part of the vendor-neutral contract. Three consequences, all real:

  • An IDE with no PLCopen export could not implement the contract at all. TIA Portal is the concrete case: Openness has its own representation and no PLCopen, so a Siemens driver was impossible for a reason that had nothing to do with Siemens.
  • TwinCAT could not adopt its own better transport, because the engine would not accept it — so PLCopen's failures on TwinCAT became Volt's failures.
  • CODESYS could not hand over the typed objects it actually has, and had to serialize a document instead.

BodyLanguage is gone for the same reason: the language now arrives inside the content. A second round-trip to ask "what language is this" was the transport leaking upward.

The vocabulary

Five types cross the seam. They are Volt's own, and a driver converts its vendor's forms into them.

typeis
ItemRefAn opaque handle to one node in the IDE's tree — a readonly struct wrapping the vendor's native object. The engine never unwraps it.
ProjectItemWhat a walk found: (Name, Item, KindCode, Folder). Name is the stable identity, Folder its path from the tree root.
WalkResultItems plus UnwalkedFolders — and Complete. See below; this is the most easily-missed part of the contract.
ItemContent(Kind, Declaration, Body, Members). One record for both directions — a read builds it, the ST writer renders it, the ST reader parses it back, a push applies it.
MemberA method, action or property, with its own declaration and body, and a property's Getter/Setter.

Why WalkResult carries completeness

Both drivers skip a subtree they cannot enumerate rather than aborting the whole walk, which is right — a transient COM fault on one folder should not fail a pull. What was missing is that they never told the caller. WalkItems() returned a plain list, and the sync layer derives deletions as "known to the client, absent from this walk" — so one faulting folder reported every item beneath it as deleted, and the pull removed the engineer's files for POUs that were still sitting in the IDE.

If you implement this interface, populate UnwalkedFolders. An entry means "there may be items under here that this walk did not see" — never "these are gone".

Threading, and why it is on the interface

Both IDE automation surfaces are single-threaded-apartment. Every IDE-touching operation is marshalled through RunOnStaThread<T>, and that is load-bearing rather than defensive: touching the object model off the IDE's own thread is how you get a hang that looks like a network problem.

DriverBase implements the parts that are identical across vendors — the degraded-state machine, the liveness bracketing around the marshal, the single-flight health probe, and the composition of the whole health response. A vendor supplies only the row snapshot. That last part is deliberate: health's wire shape used to be composed once per vendor, which is exactly how two vendors come to answer differently.

HandlesSurviveStructureChange is the other threading-adjacent fact worth knowing before you write a driver. On CODESYS a handle survives adding a child; on TwinCAT it does not, because a member is not a separate file there and placing one is a round trip through the enclosing POU's archive, which replaces the item. The reconciler used to assume the worse case for both — 19 full project walks for a POU with 20 members, on a vendor that never needed one.

The pre-flight

ValidateSource throws exactly what WriteContent would throw, for the reasons this driver can decide without touching the IDE. The push calls it for every op before it applies the first one.

The engine's own pre-flight already covers everything decidable from the source text — a malformed document, network text that does not parse or is not canonical — and that is vendor-neutral by construction. What it cannot cover is a shape one vendor cannot express. Being pure is the whole point: this was once called from inside the write, so a push whose second item carried such a shape left the first item in the project and told the caller it had failed.

DriverBase refuses nothing by default, which is the honest answer for a driver whose refusals genuinely need the live objects. A pre-flight that guesses is worse than one that declines to.

Lifting this into another project

  1. Take Volt.Engine/Ide/ and Volt.Engine/Item/. The contract, the vocabulary, DriverBase, and the shared navigation helpers (TreeNav, ItemLookup, SourceScopes). No wire, no sync.
  2. Take one driver — Volt.Ide.Codesys or Volt.Ide.Twincat — as the worked example of what a vendor implementation costs.
  3. Decide whether you want Format/. If your project wants bodies as text, yes: that is the ST layer and network text. If it only wants structure, IProjectTree alone is coherent.
  4. Leave Sync/ and Volt.Wire behind unless you want Volt's versioning and push semantics too. They sit above the seam and assume a git-shaped client.

The dependency that is not optional is Volt.Contracts: the driver contract references ConnectRequest, HealthResponse and BridgeDiagnostic. It is netstandard2.0 with no framework dependency, deliberately, so it loads in an in-process net48 host without fighting the IDE's own assemblies.
