The Volt bridge

A bridge exposes one running PLC IDE — CODESYS or TwinCAT — over a Windows named pipe, as JSON. It is how a PLC project becomes text, and how edited text goes back. These pages document both layers: the pipe wire, and the vendor driver underneath it.

The surfaces, and which one you want

Volt exposes four things, reached four different ways. They are documented separately because they are used separately — and every one of them can be called from these pages, see below.

to see or change which bridges are running 5 routesHTTP :8550 The connector
to sync a workspace from a terminal or a script 11 verbsargv The CLI
to drive a PLC IDE from your own program IIdeDriverin-process The driver layer

Calling them, not just reading about them

A description is worth what you can check, and none of these three can be exercised from a page: a browser cannot open a named pipe, the connector refuses cross-origin requests by design, and argv is not something a page has. So the volt binary serves these same files from a process that reaches all three: 

volt console                  # read-only — every call runs, nothing can change a project
volt console --allow-write    # enables push, the mutating verbs, and control-plane writes

Every op, route and verb then carries a Send panel with an editable request and the raw answer — including the progress frames a wire op streams, and the exit code a CLI verb returns. Opened as plain files instead, the pages render identically and say plainly that nothing can be called.

The wire is the parity boundary: both vendors serve byte-identical responses for the same project, so a client never learns which IDE it is talking to except by asking. Everything that could differ is resolved below the driver seam, as data, never as a branch in a caller.

The shape of a session

Every client does the same four things, in the same order. Nothing here is vendor-specific.

sequenceDiagram participant C as client participant B as bridge participant I as IDE C->>B: health B-->>C: projects + liveness (from the cached snapshot) C->>B: connect { project } B->>I: bind B-->>C: ok — or PLC_DISCONNECTED C->>B: init B->>I: walk + read every item B-->>C: progress… then every item as text Note over C: edit the text C->>B: push { expectedProjectVersion, ops } B->>B: PRE-FLIGHT — every text-decidable refusal, before the first write B->>I: apply B-->>C: accepted — or conflicts, with nothing written

The pre-flight is the rule worth knowing before you build anything on this: a push that cannot land in full lands nothing. Everything refusable from the source text alone is decided before the IDE is touched.

Reaching a bridge

One pipe per live IDE, named volt.bridge.<vendor>.<pid> where the suffix is the IDE process id. Discover by prefix — the pid changes whenever the IDE restarts, so a hard-coded full name is a bug waiting for the next restart.

Vendors: 

# every live bridge on this machine
[System.IO.Directory]::GetFiles("\\.\pipe\") -match 'volt\.bridge\.'

Framing is newline-delimited JSON, one request object per call. See Transport & framing for the response frames, including the progress stream long ops emit before their result.

Serving one for development

One script serves either vendor against a committed fixture project — never your own live IDE: 

pwsh scripts/ide.ps1 up -Vendor codesys   # or: twincat
pwsh scripts/ide.ps1 pipe                 # print the pipe it is serving
pwsh scripts/ide.ps1 logs
pwsh scripts/ide.ps1 down

The vendors differ in exactly one step and the script owns it: CODESYS loads the bridge in-process, TwinCAT needs a separate VoltBridgeTwincat --xae-pid worker. A GUI IDE stays clickable while a suite drives it, because the IDE's own message loop is what answers the pipe.

Keeping these pages true

Every table of facts here — the ops, their error codes, the schemas, the item kinds, the driver members — is reflected out of the types the runtime uses, and the build fails if a page and the code disagree. So a table on these pages is as current as the code it came from. 

# after changing a contract type, an item kind or a driver interface
VOLT_WRITE_DOCS=1 dotnet test test/Volt.Engine.Tests

volt-bridge.openrpc.json is the same wire as a machine-readable OpenRPC document — the file to hand to another project. npx @open-rpc/generator turns it into a typed client.
