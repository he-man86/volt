# CODESYS ⇄ TwinCAT: the measured vendor facts

**The one home for vendor facts.** It lives beside the contract they constrain (`Ide/`), not in a change folder,
because a change gets archived and these facts do not stop being true. When a measurement lands, correct it HERE
and delete the claim from wherever else it crept into a doc-comment.

Every row is cited from code by id (`DIALECT D4f`). `bun run check` fails if code cites an id that does not
exist here, or one marked `[RETRACTED -> X]` — both have happened, which is why the check exists.

> **This file was deleted once, by accident.** It lived under `PlcOpen/` and went out with that transport, while
> fourteen citations in production code kept pointing at it — including the justification for why TwinCAT
> re-finds a handle after every member create. The facts had outlived the layer they were filed under. It is
> filed under `Ide/` now because that is what they are about: how the two IDEs behave, not how one transport
> used them.

## The structural conclusion

> **The two vendors share an object model and differ only in ACCESS.** Measured 2026-08-29 by reflecting over
> both shipped `NWLObject.dll` assemblies: every interface Volt's graphical model uses is member-for-member
> identical. CODESYS hands over the live objects; TwinCAT hands over their serialization. Nothing in the engine
> branches on a vendor name, and nothing should start — what differs lives below the `Ide` seam, in the two
> drivers.

There is deliberately **no dialect abstraction**. The gap between the two vendors is not missing indirection, it
is missing EVIDENCE. Every entry cites code, a recorded fixture, or is marked **UNMEASURED** — `bun run check`
lists every marker on every run. Paths are relative to `packages/volt-cli/`.

| **N2** | **The aspect's TYPE is the language on CODESYS — dispatch is a cast, not a lookup.** `STImplementationObject` / `NWLImplementationObject` / `CFCImplementationObject`. | **N4** | **The archive is a STRICT typed object graph with a per-type member contract.** The reader consumes members in order for the type it expects, so a member set that is close but not exact makes it mis-assign everything after the discrepancy. ## Structure, placement and handles

| id | fact |
|---|---|
| **C2a** | **The export WORKS, and the E_FAIL was ours.** Measured: `PlcOpenExport` exports a root DUT (2012 chars, `<dataType>`), a root GVL (1983, `<globalVars>`) and a FOLDERED DUT (`VltProbeF.VltProbeDutF`). What fails is a BARE name for a foldered item — `PlcOpenExport('PLC_PRG')` answers *"Selection 'PLC_PRG' not found!"* — because the selection grammar is the DOTTED project-relative path, which `PouSelectionPath` already builds. The recorded E_FAIL came from `ExportPouXml` calling `EnclosingPou`, which climbs `node.Parent` until it finds a POU; for an item that has none the walk runs off the top of the tree, where `Parent` throws COMException E_FAIL. `PlcOpenExport` was never reached, so the vendor never refused anything. Fixed by choosing the export target by KIND (`IsInlinedInPou`), which cannot run off the tree |
| **C2b** | **AND THE SECOND REASON WAS ALSO OURS: `623` IS `TREEITEMTYPE_PLCDUTALIAS` ON TWINCAT, NOT A GENERIC DUT.** With the export fixed, DUT creates still failed — TwinCAT's importer validates against TC6 and rejected an empty `<baseType/>` as "incomplete content". True, and the object was malformed before any export: `CreateChild` refuses a null vInfo for 623 (*"Base class not specified!"*) and takes any string as the alias's BASE CLASS, so Volt — passing the body language — created every DUT as an alias to a type named **"ST"**. The per-child write only survived it because `WriteText` landed the real declaration afterwards; the document path exports first. Measured, creating with the real subtype: **606 → `<baseType><struct/>`, 605 → `<baseType><enum><values>`, 607 → union — all three round-trip their own export AND take a spliced declaration.** And one seed serves all four: create **606** and let the pushed declaration re-derive, exactly as CODESYS does with `DutType.Structure` — struct stays 606, an enum declaration becomes 605, a union 607, and an alias (`: INT;` or `: STRING(80);`) becomes 623 with the right base. `TcObjectModel.CreateChild`. **Every source kind now travels as ONE PLCopen document on both vendors; the `CanExportDocument` capability added for this is deleted** |
| **C2d** | **CODESYS's `create_pou` DOES take an implementation language.** Enumerated off the live scripting container: `create_pou(name: String, type: PouType [opt], language: Nullable\`1 [opt], return_type: String [opt], base_type: String [opt], interfaces: String [opt])`, and `create_function`/`create_function_block`/`create_program` each take one too. `CodesysObjectModel.CreateChild`'s "CODESYS's create_pou has no implementation-language parameter" was an inference. Volt still seeds and lets the import set the language, which works — but the reason recorded for it was false |
| **D4d** | **NEW — a TwinCAT PLCopen import INVALIDATES every handle to the item it replaced.** Any later COM call on that handle answers *"Item 'x' is deleted or invalidated by an ealier operation!"*. CODESYS's merge does NOT do this, and `PushService` carried the CODESYS reading as a general one ("`WriteXml` is a merge with no delete, so `pou` is not stale") — true there, false here. A graphical push reaches `RemoveOrphanChildren` immediately after `NetworkCode.Write` has imported, so on TwinCAT it was reconciling through a dead handle. **It went unseen for as long as it did because `BeckhoffDriver.ChildCount` caught the fault and answered `0`**: the orphan walk became a silent no-op, so a method deleted from a graphical POU survived in the IDE — the very bug the walk had been made unconditional to fix, still happening one layer down. Fixed by re-acquiring the item after the content write (`ItemLookup.Find`, hard-failing on a miss); the driver's accessor no longer fabricates `0`, so the next such fault is loud |
| **D4f** | **THE MOVE EXISTS. D4 and C5 were both wrong, and each for a reason worth keeping.** The dispatch surface of `ITcSmTreeItem` was ENUMERATED — `IDispatch::GetTypeInfo` → `ITypeInfo::GetFuncDesc`/`GetNames` on a live tree item — instead of probed by name. There is genuinely no `Move`/`Reparent` member; that half of D4 holds and is now settled rather than assumed. What the enumeration also gave was the real signatures, which two earlier probes had guessed at: `PlcOpenImport(bstrFile, options, bstrSelection, bFolderStructure)` — **four** arguments, of which Volt has ever passed two, and D4b's "a third argument naming a target folder is `DISP_E_TYPEMISMATCH`" was landing on `bstrSelection`, never reaching the folder flag at all. And `ExportChild(bstrName, bstrFile)` / `ImportChild(bstrFile, bstrBefore, bReconnect, bstrName)`. **The archive is a plain zip and the item's source path is an ENTRY NAME** — that is the "way to rewrite the path inside the archive" D4 said had not been found. Measured, all four cells: exporting `VltProbeF/VltProbePou` yields one entry `VltProbeF\VltProbePou.TcPOU` and importing it into `VltProbeG` gives `VltProbeG/VltProbeF/VltProbePou` (D4's path recreation, reproduced); **rename that entry to `VltProbePou.TcPOU` and the same import gives `VltProbeG/VltProbePou`** — a true move. It carries CHILDREN (an FB with a method arrives with `childCount=1`) and therefore graphical bodies, which `PushService`'s delete-and-recreate move can never do. Implemented as `TcItemArchive.Move`; only entry names are rewritten, every entry's bytes are copied through untouched |
| **D4j** | **AND IT IS RESTORABLE — the member's folder is an attribute in the POU's OWN file. This was the last thing blocking the single-document write on TwinCAT, and it is closed.** `ExportChild` REFUSES a member — *"The tree item 'Deep' cannot be exported seperately because it has no document file. Please export the parent node that contains the document!"* — which reads like the end of the road, and is instead the whole clue: a member is not a file because TwinCAT keeps the entire POU, members and all, in ONE `.TcPOU`. Read that file and the placement is right there. Measured live, the complete shape: `<Folder Name="Helpers" Id="{guid}">` elements that NEST by element, one path segment each; and on the member `FolderPath="Helpers\Inner\"` — full path, backslash-separated, TRAILING separator — with the SAME attribute on `<Method>`, `<Action>` and `<Property>` alike. So the relocation happens one level up: export the POU, rewrite the attribute (and create the `<Folder>` chain), delete, re-import. Verified on a textual AND an FBD member in one go: both land in the folder, bodies intact — the archive is the vendor's own format, so nothing is rebuilt from text. Cost, and it is real: placing a member is a full POU round trip, so a POU with N foldered members pays N of them, and each one INVALIDATES every handle into that POU. `PushService.RestoreChildFolders` therefore re-finds the POU once per member — it used to hoist that lookup out of the loop, which was correct only while CODESYS (whose move touches nothing but the moved object) was the sole driver that reached it |
| ~~D9~~ | **CLOSED — the grammar is the DOTTED project-relative path.** `POUs.PLC_PRG` and `VltProbeF.VltProbeDutF` export; a BARE name resolves only at the PLC-project root, and for a foldered item answers *"Selection 'x' not found!"*. That refusal, read as a vendor limit, is what produced the retracted C2 — see C2a |

Read with `MetadataLoadContext` (or a raw `MetadataReader`, which loads nothing at all) every sibling appears. The row's CONCLUSION survives intact for a different reason — see N12 — but its central piece of evidence was false. |

(c) **What DOES travel is the topology, and it is resolved properly.** From a document stating only boxes, operands and wires, TwinCAT built a complete archive: `BoxTreeAssign` with `OutputItems` `out1`/`out2` over a `BoxTreeBox` `AND` with `InputItems` `a`/`b`, `CallType Operator=And`, and every `Id` minted by the IDE — i.e. exactly the members Volt must never guess (C2b's lesson, and the reason `TcNetworkWriter` creates nothing). | **D23** | **A freshly created graphical POU is FULLY PRESENT AND ENTIRELY BLANK, so "has no body" is not a blankness test.** `CreateChild` with a graphical language mints a complete archive — `NWLImplementationObject`, a `TypeList`, and one `Network` whose `NetworkItems` is empty (`EmptyGraphicalShell.TcPOU`, saved from the live IDE). `string.IsNullOrWhiteSpace(implementation)` therefore never fires on a create, and the push fell through to the in-place writer, which refused with "network 1 changes from 0 to 1 item(s)". The rule that holds is `TcArchive.HasNoItems`. And explicitly NOT "the archive root is null": that is also true of a TEXTUAL body, so routing on it would silently convert live ST into a diagram instead of refusing. |
| **D24** | **A BOX'S OWN OUTPUT PINS CANNOT BE COMPARED AGAINST A PUSHED MODEL — network text has no syntax for them.** `Outputs` appears nowhere in `NetworkTextWriter` or `NetworkTextReader`, so a text-derived `Box.Outputs` is ALWAYS empty, and `TcNetworkWriter` was comparing the archive's count against information the model can never carry. It could only pass when the archive's box also had zero outputs — true of every hand-authored fixture, and FALSE of every box the IDE has resolved: TwinCAT gives a resolved `AND` one output item holding an empty operand. The consequence was that such a body could be pulled and never pushed back ("an item changes from 1 to 0 output(s)" on a push that changed nothing), which went unseen only because no fixture had one until an import produced the first. An ASSIGNMENT's targets are a different thing and ARE carried by the text (`out := x`), so those are still written. |
| **D25** | **A PLCopen import DECIDES ITS OWN NETWORK BOUNDARIES, so the archive's shape is the IDE's answer and not a copy of what was pushed.** PLCopen FBD has no network element — the body is a flat list of `inVariable`/`block`/`outVariable` wired by `refLocalId` — and the importer groups them by what is actually WIRED TOGETHER. Measured: one network holding two disconnected statements (`t1(IN := a, PT := pt); done := t1.Q;`) comes back as TWO networks. Volt's per-network `localId` spacing (`10^10 * (order+1)`) does keep separate networks separate, but it cannot hold disconnected trees together inside one. **Measured across four shapes and now GATED** (`test/e2e/graphical/grouping.test.ts`): one connected tree → 1; one wire feeding two coils → 1 (a shared `refLocalId` is still ONE component); two disconnected sinks → 2; an FB call plus a separate output read → 2. **The rule is therefore ONE NETWORK PER CONNECTED COMPONENT, and it is predictable from the model before the IDE is touched** — `TcNetworkWriter.Unhoist` already folds shared-wire trees into one item, so the component count is its result count. That is what makes a per-network SPLICE sound: a single-component network can be rebuilt by the IDE and swapped back in, leaving every other network byte-identical, while a multi-component one is refused because re-creating it would split it and renumber everything after it. **One trap:** the `localId` also encodes the network INDEX, so a network rebuilt while still carrying its real `Order` makes the importer emit the empty networks in front of it too (an `Order` of 1 came back as 2 networks). A rebuilt network is renumbered to 0 — its real position is the slot it is spliced into, which the rebuild has no need to know. The consequence is that the in-place archive writer, which requires the model and the archive to agree on shape, legitimately refuses after a create — so a create stamps values through it only when the shapes match, keeps the IDE's grouping when the model carries nothing beyond structure, and FAILS when the model carries detail the import cannot express. |
| **D26** | **COIL STORAGE LIVES ON THE ASSIGNMENT TARGET IN THE ARCHIVE AND ON THE VALUE IN NETWORK TEXT — and nothing translated between them.** The archive puts `Set` on the `BoxTreeAssign`'s OutputItems operand (measured on a real ladder: `Flags=Negation,Set`); the published text format spells it as a trailing modifier after the VALUE (`out := a SET;`), and `NetworkTextWriter` renders modifiers from the value, never from the target. So a SET coil pulled from TwinCAT rendered as a PLAIN one: invisible in the workspace, and silently downgraded on the next create. **It hid behind a green round-trip test**, because the writer did not write target flags either — the archive kept its SET, nothing appeared to change, and the loss was only in what the engineer could see. CODESYS's reader already puts storage on the value, so translating here is the two vendors agreeing, not a TwinCAT special case. The write back is BIT-PRECISE rather than a whole-flags assignment: a target may carry modifiers the text has no form for (a negated coil), and rewriting the field wholesale would erase them on a push that never mentioned them. `Reset` still refuses — the vendor's flag set has no such bit. |
| **D27** | **The library-signature format, measured — and it closes C2c.** C2c established that `_ITcPlcLibraryManager.ProduceAllLibrarySignatures()` WORKS out-of-process while Volt implemented no extraction; what was still missing was the shape of what it returns, which no fixture recorded. Captured live with `--probe-libsig` (181,179 chars on the fixture, now excerpted verbatim as `fixtures/tc-pou/library-signatures.xml`): **it is XML, and it is NOT one document** — each referenced library is emitted as its own `<Library>` root and they are CONCATENATED, so three libraries come back as three roots and any parser rejects the payload until it is wrapped. Each root carries `LibraryName` / `Version` / `Distributor`, which are precisely the three parts `LibraryManifest.Resolution` formats — so the join from a signature to its `.library` ref falls out instead of being guessed. Inside, `<TypeSignature type="…">` takes exactly five values, and they are the SAME five strings `LibSignatureRenderer` already switches on (both are 3S vocabularies): **`FunctionBlock` (102), `Function` (114), `Type` (25), `VarGlobal` (18), `Interface` (1)**. A FUNCTION's RETURN arrives as an `<Output>` NAMED AFTER THE FUNCTION (`CONCAT` → `STRING(255)`), which is exactly the shape `LibSignatureRenderer.LiftReturn` already lifts. **The surface is SHALLOWER than CODESYS's in one way that matters: `Type` and `Interface` are described by NAME ONLY** — no fields, no methods, on every one of the 26 — so Volt does not emit them. Rendering a member-less `Type` would produce `TYPE X : STRUCT END_STRUCT END_TYPE`, which does not omit the fields but ASSERTS THERE ARE NONE, turning every `x.field` an engineer writes into a false error; emitting nothing costs one unknown-type error at the declaration instead of a wrong one at every use. There are also no METHODS anywhere in this surface, so a library FB's methods are not resolvable on this vendor as they are on CODESYS. Measured end to end: 181,179 chars → 234 signatures → 230 shipped (26 name-only skipped by design, 4 return-less FUNCTIONs render-null — the same D20 class CODESYS hits). |
| **C7** | **AN UNWIRED `En` PIN READS AS `System.Boolean false`, NOT NULL — and it cost a whole POU.** Probed on a user's project: a plain `AND` box in a network an ENGINEER drew reports `En = False`. `CodesysNetworkReader` treated any non-null `En` as a WIRED enable and handed it to `ReadNode`, which dispatches on the runtime type name, found `Boolean`, and threw *"the graphical item 'Boolean' has no network-text form yet"*. The damage ran far past a missing enable: that throw makes the BODY unreadable, an unreadable body makes the ITEM unreadable, and `FetchService` then SKIPS it — so the POU was absent from the workspace entirely, with no error at the wire and no file in git. **It reached a user before a test because every graphical fixture Volt owns is one Volt itself created, and those carry a null `En`; only a body drawn in the IDE has the boolean.** The guard is applied to every node-valued member (`RValue`, `Input`, `En`, `GetTree`), not just `En`: they are read the same way and nothing says the vendor is consistent about which of them answers `false`. **It now HAS an offline gate**, which it did not when this row was written. `NwlInterop` reaches every vendor member by reflection and the reader dispatches on `GetType().Name`, so a plain C# class NAMED `BoxTreeBox` with `En = false` reproduces the shape exactly — `Volt.Ide.Codesys.Tests` (net48, like the in-proc host) does it in milliseconds with no IDE, and reverting the guard reproduces the original message verbatim. |
| **C8** | **A NETWORK'S TITLE AND COMMENT CARRY THE NEWLINE THE ENGINEER TYPED.** Measured on the same project: `Title = "testlabel\r\n"`, `Comment = "this is a comment\r\n"`.
