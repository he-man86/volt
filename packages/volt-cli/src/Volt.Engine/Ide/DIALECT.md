# CODESYS ⇄ TwinCAT: the measured vendor facts

**The one home for vendor facts.** It lives beside the contract they constrain (`Ide/`), not in a change folder,
because a change gets archived and these facts do not stop being true. When a measurement lands, correct it HERE
and delete the claim from wherever else it crept into a doc-comment.

Every row is cited from code by id (`DIALECT D4f`). `bun run check` fails if code cites an id that does not
exist here, or one marked `[RETRACTED -> X]` — both have happened, which is why the check exists.

> **This file was deleted once, by accident.** It lived under `PlcOpen/` and went out with that transport, while
> fourteen citations in production code kept pointing at it — including the justification for why TwinCAT
> re-finds a handle after every member create. The facts had outlived the layer they were filed under. It is
> filed under `Ide/` now because that is what they are about: how the two IDEs behave, not how one transport
> used them.

## The structural conclusion

> **The two vendors share an object model and differ only in ACCESS.** Measured 2026-08-29 by reflecting over
> both shipped `NWLObject.dll` assemblies: every interface Volt's graphical model uses is member-for-member
> identical. CODESYS hands over the live objects; TwinCAT hands over their serialization. Nothing in the engine
> branches on a vendor name, and nothing should start — what differs lives below the `Ide` seam, in the two
> drivers.

There is deliberately **no dialect abstraction**. The gap between the two vendors is not missing indirection, it
is missing EVIDENCE. Every entry cites code, a recorded fixture, or is marked **UNMEASURED** — `bun run check`
lists every marker on every run. Paths are relative to `packages/volt-cli/`.

## The object model (measured 2026-08-29, both assemblies reflected)

| id | fact |
|---|---|
| **N1** | **The NWL object model is IDENTICAL on both vendors, member for member.** TwinCAT ships `NWLObject.dll` 3.5.13.0 + `NWLObject.plugin.dll` (the concrete types) under `C:\TwinCAT\3.1\Components\Plc\`; CODESYS ships 4.1.0.0. Reflected: `INetwork` 27/27 members, `IOperand` 17/17, `IFlags` 18/18, `IBoxTree` 6/6, `IBoxTreeVisitor` 3/3, `IOutputItemList` 5/5, `IBoxTreeDemux` 5/5. 59 vs 61 types; the ENTIRE difference is `IPLCopenXMLAddDataProviderNWL` + `IPLCopenXMLAddDataReaderNWL`, CODESYS-only and dead with the PLCopen transport. A two-major-version gap and nothing Volt touches differs. So `CodesysNetworkReader`/`Writer` would port to TwinCAT unchanged — what is missing is ACCESS, not the model |
| **N2** | **The aspect's TYPE is the language on CODESYS — dispatch is a cast, not a lookup.** `STImplementationObject` / `NWLImplementationObject` / `CFCImplementationObject`. Nothing sniffs content and no language query is needed. Measured on one project: 271 ST + 1 CFC; on another 38 ST + 36 NWL |
| **N3** | **TwinCAT's `ImplementationText` IS the `<NWL><XmlArchive>` for a graphical body**, and `ImplementationXml` returns the SAME string — measured on a live POU, 7068 chars both. There is no second, richer representation over COM. `Language` is NOT on the object at all (RuntimeBinderException), so the body language is read from the archive's `DefaultViewMode` |
| **N4** | **The archive is a STRICT typed object graph with a per-type member contract.** The reader consumes members in order for the type it expects, so a member set that is close but not exact makes it mis-assign everything after the discrepancy. Measured against vendor-written `POU_PBD.TcPOU`: a `BoxTreeBox` carries `BoxType, Instance, OutputItems, Flags, InputFlags, InputItems, InputParam, OutputParam, CallType, EN, ENO, STSnippet, ContainsExtensibleInputs, ProvidesSTSnippet, Id`; a `BoxTreeOperand` carries `Operand, Id` and NO Flags; every item and operand carries `Id`. Writing an inferred subset produced twenty `.TcPOU` files TwinCAT could not open (`Value cannot be null. Parameter name: iILStatement`). **`TcNetworkWriter` therefore edits values in place and constructs nothing** |
| **N5** | **`CallType` is a SCALAR with a type attribute** — `<v n="CallType" t="Operator">And</v>` — not an object member. Reading it with an object accessor found nothing and classified every operator box as a plain function call |
| **N6** | **TcXaeShell is 32-bit and hosts the .NET FRAMEWORK CLR** (`clr.dll`, `Framework\v4.0.30319`). Any in-proc host must be net4x, x86/AnyCPU — a sibling of `Volt.Ide.Codesys` (net48), never the net10/x64 worker. **UNMEASURED:** whether the NWL objects are reachable from inside that process. `Process.Modules` across the WOW64 boundary cannot answer it — the same enumeration also fails to show `Microsoft.VisualStudio.Shell`, without which the shell cannot run — and enumerating `DTE.Commands` out-of-process hangs |
| **N7** | **`ITcPlcPou.DocumentXml` is a GET AND SET of the whole POU**, children included, in the vendor's own `TcPlcObject` format — 7742 chars for a POU whose body archive is 7068. Unused. It is the one-call write the per-child path lost, and unlike PLCopen it is not a translation. **UNMEASURED:** whether `set_DocumentXml` replaces children as well, and whether a vendor-written document round-trips through it byte-identically — which must be proven before it is used, per N4 |
| **N8** | **`ProduceXml` returns TwinCAT's `<TreeItem>` METADATA schema, not the file format.** An interface's own XML lists `ItemName, PathName, ItemType, ItemId, ChildCount, PlcItfDef, DeclarationExport, DocumentExport, VSProperties` — and carries no `<Property>` elements, so a property's accessors cannot be read from it. `ProduceXml()` with no argument omits children entirely; `ProduceXml(true)` includes them |
